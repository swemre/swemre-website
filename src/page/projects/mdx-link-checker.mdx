**mdx-link-checker** is a command-line tool that finds broken links in MDX and Markdown content before they reach production: routes that no longer exist, anchors that were renamed, images that were moved and external pages that have disappeared. It understands MDX the way the site's own build does, runs without starting a server, and is fast enough to run on every commit.

## The problem

Content sites rot quietly. Nothing crashes when a link breaks; a reader just lands on a 404 or at the top of a page instead of the section they wanted. The usual causes are mundane:

- An article slug is renamed and nobody updates the three other articles that link to it.
- A heading is reworded, which changes its generated id, and every `#anchor` link to it silently stops scrolling.
- An image is moved into a subfolder.
- An external page is deleted or moved by its owner, years after you linked to it.

General-purpose link checkers crawl a running site. That works, but it is slow, needs a server, and reports problems far from where they were introduced: in a crawl report instead of next to the line in the source file. For a site whose content lives in a repository, the better place to check links is the source.

## Goals

| Goal                      | Meaning                                                            |
| ------------------------- | ------------------------------------------------------------------ |
| Source-level              | Read `.mdx` and `.md` files directly; report file, line and column |
| Same parser as the site   | Use the same `remark` plugins, so links are seen exactly as rendered |
| No server                 | Validate internal links against an index, not by HTTP requests     |
| Fast in CI                | Under two seconds for a few hundred files without external checks  |
| Polite to the internet    | External checks are opt-in, cached and rate-limited                |
| Helpful output            | Suggest the closest valid anchor or slug for typos                 |

### Non-goals

- Checking links inside rendered React components that are computed at runtime.
- Crawling a live site.
- Rewriting content automatically (suggestions only, with an explicit flag to apply them).

## What it checks

| Link kind            | Example                         | Check                                      |
| -------------------- | ------------------------------- | ------------------------------------------ |
| Internal route       | `/articles/some-slug`           | Route pattern matches and the slug exists  |
| Heading anchor       | `#data-model`                   | A heading with that id exists on the page  |
| Cross-page anchor    | `/projects/x#approach`          | Both the page and the heading exist        |
| Relative file        | `./diagram.svg`                 | File exists relative to the source         |
| Public asset         | `/images/diagram.svg`           | File exists in `public/`                   |
| External URL         | `https://example.com/page`      | Request returns 2xx or 3xx (opt-in)        |
| Email and phone      | `mailto:`, `tel:`               | Syntax only                                |

## Architecture

The tool runs in three phases. Each phase is a pure function over the output of the previous one, which keeps it easy to test.

```text
 ┌────────────┐     ┌──────────────┐     ┌──────────────┐     ┌───────────┐
 │  Discover  │ ──► │    Index     │ ──► │   Validate   │ ──► │  Report   │
 │ glob files │     │ routes, ids, │     │ every link   │     │ text/json │
 │            │     │ assets       │     │ vs. index    │     │ /sarif    │
 └────────────┘     └──────────────┘     └──────────────┘     └───────────┘
```

### Phase 1: discover

Expand the input globs, read each file and parse it into an MDX syntax tree with the same plugin list the site uses (for this site, `remark-gfm`). Parsing with the site's own configuration matters: GitHub-flavoured Markdown turns bare URLs into links, and a checker that does not know that would miss them.

### Phase 2: index

Walk every tree once and build an index:

```ts
interface LinkIndex {
  routes: Map<string, PageEntry>
  assets: Set<string>
}

interface PageEntry {
  file: string
  headingIds: Set<string>
}
```

Routes come from a small configuration file that maps folders to URL patterns:

```json
{
  "routes": [
    {"pattern": "/articles/:slug", "files": "src/page/article/*.mdx"},
    {"pattern": "/projects/:slug", "files": "src/page/projects/*.mdx"},
    {"pattern": "/sp/:slug", "files": "src/page/sp/*.mdx"}
  ],
  "static": ["/", "/articles", "/projects"],
  "public": "public"
}
```

Heading ids are generated with the same slug function the site uses. This is the single most important detail in the design: if the checker and the site disagree about how "What's next?" becomes an id, every anchor to that heading is a false positive or, worse, a false negative. The configuration can point to the site's own slug function so they can never drift.

### Phase 3: validate

Collect every link node (Markdown links, images, reference definitions and `href` or `src` attributes on JSX elements with literal string values) and check each against the index. Links built from expressions, such as `` href={`/articles/${slug}`} ``, are reported as "skipped: dynamic" in verbose mode instead of being guessed at.

## External links

Checking external URLs is the slow, flaky part, so it is opt-in with `--external` and designed to be polite:

- **HEAD first**, falling back to GET for servers that reject HEAD.
- **Concurrency limit** per host (default 2) and globally (default 8).
- **Cache** results for 24 hours in a small JSON file, keyed by URL, so repeated CI runs do not hammer the same sites.
- **Timeouts** of 10 seconds; a timeout is a warning, not an error.
- **Allow list** for sites that block automated requests, configured per project.

External failures are warnings by default. A link that was fine yesterday and 503s today should not block a deploy.

## Output

Output is grouped by file, with line and column numbers that editors and terminals can jump to:

```text
src/page/article/getting-started-with-mdx.mdx
  42:7  error  Unknown anchor "#instal" (did you mean "#install"?)
  58:3  warn   https://example.com/old returned 404

src/page/projects/token-forge.mdx
  17:12 error  Unknown route "/articles/token-only-design-system"
               (did you mean "/articles/token-only-design-system-tailwind-v4"?)

2 errors, 1 warning in 2 files (31 files checked, 214 links)
```

Machine-readable formats are available with `--format json` and `--format sarif`. SARIF lets GitHub show the problems as annotations on the pull request, right next to the offending line.

### Suggestions

For unknown anchors and slugs, the tool computes the edit distance to every known candidate on the same page (for anchors) or in the same route (for slugs) and suggests the closest one under a threshold. Most broken links are typos or small renames, so the suggestion is right far more often than not.

`--fix` applies suggestions whose distance is small and unambiguous, prints every change, and refuses to run on a dirty working tree, so the result is always a reviewable diff.

## Usage

```bash
npx mdx-link-checker "src/page/**/*.mdx" --config links.json
npx mdx-link-checker "src/page/**/*.mdx" --external --format sarif > links.sarif
```

| Flag              | Effect                                                      |
| ----------------- | ----------------------------------------------------------- |
| `--config <file>` | Route and asset configuration                               |
| `--external`      | Also check external URLs                                    |
| `--format`        | `text` (default), `json`, `sarif`                           |
| `--fix`           | Apply safe suggestions                                      |
| `--max-warnings`  | Fail when warnings exceed the given number                  |
| `--verbose`       | Show skipped dynamic links and cache hits                   |

Exit codes: `0` for no errors, `1` for errors, `2` for configuration problems. Warnings never fail the run unless `--max-warnings` says so.

## Integration

The natural place to run it is next to the other quality gates:

```json
{
  "scripts": {
    "links": "mdx-link-checker \"src/page/**/*.mdx\" --config links.json",
    "links:external": "npm run links -- --external"
  }
}
```

Internal checks run on every commit; they are fast and deterministic. External checks run on a nightly schedule, where a flaky third-party site cannot block anyone's work.

## Editor integration

Finding a broken link in CI is good; never typing one is better. Because the index is built from the same files the editor has open, the core can also power an editor extension:

- **Diagnostics** underline unknown routes and anchors as you type, with the same messages as the CLI.
- **Completion** offers known slugs after `/articles/` and known heading ids after `#`, so links are picked rather than typed.
- **Rename support**: renaming a heading offers to update every anchor that points to it across the repository.

The extension reuses the index and validation phases unchanged; only the reporting layer differs. Keeping the core free of terminal and file-system assumptions is what makes this possible, and it is another reason each phase is a pure function.

## Performance

Most of the time goes into parsing. A rough budget for this site's size:

| Step                         | Cost per file        | 300 files    |
| ---------------------------- | -------------------- | ------------ |
| Read and parse MDX           | about 3 ms           | about 0.9 s  |
| Index headings and links     | under 0.5 ms         | about 0.15 s |
| Validate internal links      | microseconds per link | negligible  |

Parsing runs on a small worker pool sized to the machine's cores, which brings a few hundred files well under the two-second goal. A content hash cache can skip unchanged files entirely between runs, which matters more for large documentation sites than for a personal one.

These figures are estimates for planning, to be replaced by measurements once the first version exists.

## Testing strategy

Because each phase is a pure function, most tests need no file system:

- **Index tests**: a handful of in-memory documents produce the expected routes and heading ids, including duplicate headings (`setup`, `setup-1`) and headings with punctuation or code.
- **Validation tests**: a table of link and index pairs with the expected result for each, covering every link kind in the table above.
- **Suggestion tests**: typo distances at and just beyond the threshold.
- **External tests**: a local HTTP server returning scripted status codes, timeouts and redirects.
- **End-to-end**: run the CLI on a fixture folder and compare output with a snapshot.

The site's own content is the first real corpus. If the tool reports zero problems on it, and finds the problems deliberately planted in a fixture copy, it is ready.

## Design decisions

- **Why not crawl?** Crawling finds problems late and far from their cause. Source-level checking finds them in the file that introduced them, before merge.
- **Why reuse the site's parser and slug function?** Because the only definition of "correct" that matters is what the site renders. A checker with its own rules produces noise.
- **Why are external failures warnings?** The internet is not deterministic. Errors must be reproducible, and a third-party outage is not.

## Risks

| Risk                                                       | Mitigation                                         |
| ---------------------------------------------------------- | -------------------------------------------------- |
| Slug function drifts from the site's                        | Import the site's function through configuration   |
| Dynamic links produce false negatives                       | Report them as skipped in verbose mode             |
| External checks get rate-limited                            | Per-host limits, caching, allow list               |
| Large sites make the index slow                             | Single pass per file; parallel parsing             |

## Open questions

- **Redirects.** When a slug is renamed, the site may keep a redirect from the old URL. Should links to a redirected route be errors, warnings or silently accepted? The current plan is a warning with the new target, so content gradually moves to canonical URLs.
- **Links in component props.** A `<Callout>` or a card component may take a link as a prop with a name other than `href`. A small mapping in the configuration (component name to prop names) would let the checker validate those too.
- **Localised sites.** Routes with a language prefix multiply the index. The route configuration can express it, but the suggestion engine should prefer candidates in the same language.
- **Anchors generated by components.** Some components render their own headings at runtime. Those ids cannot be seen in the source, so they need to be declared in configuration or the links to them will be reported as unknown.

None of these block the first milestone, which only needs plain Markdown links and the site's own routes.

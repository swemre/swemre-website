**Local-first notes** is a note-taking app designed around one principle: the device in your hand is the source of truth. Notes open instantly, editing never waits for a network, and the app keeps working on a plane, in a tunnel or on hotel Wi-Fi. When a connection is available, changes sync between your devices in the background and merge without asking you to pick a winner.

## The problem

Most note apps are thin clients over a server. They look fast on a good connection, but every action is a request:

- Opening a note shows a spinner while it downloads.
- Typing on a flaky connection produces "saving…" banners and, occasionally, lost edits.
- Editing the same note on a laptop and a phone produces a conflict dialog that asks you to choose which version to throw away.

The local-first movement, described in the 2019 Ink & Switch essay "Local-first software", argues for the opposite arrangement: keep the primary copy of the data on the device, and treat the server as a sync and backup service. This project applies that idea to the simplest useful case, plain-text notes.

## Goals

| Goal                       | Meaning                                                         |
| -------------------------- | --------------------------------------------------------------- |
| Instant                    | Every read and write hits local storage; no spinners for your own data |
| Offline by default         | Full functionality with no network, indefinitely                |
| Conflict-free merging      | Concurrent edits on two devices merge automatically             |
| Installable                | Ships as a progressive web app with an app icon and offline start |
| Private                    | Notes can be end-to-end encrypted; the sync server sees ciphertext |
| Boring server              | The server stores and relays opaque changes; no merge logic     |

### Non-goals

- Real-time collaborative editing between different people (possible later with the same data model, but not the first target).
- Rich text, embeds or attachments in the first version.
- A web-only mode that works without installing or storing anything locally.

## Architecture

```text
┌──────────────────────── Device ────────────────────────┐
│                                                         │
│  UI (React) ──► Note store ──► Change log (IndexedDB)    │
│      ▲              │                 │                  │
│      └── live query ┘                 ▼                  │
│                              Sync worker (background)    │
└──────────────────────────────────────┬──────────────────┘
                                       │  HTTPS / WebSocket
                                       ▼
                            Sync server: append-only log
                            per user, stores ciphertext
```

The UI never talks to the network. It reads and writes the local store, and a background worker exchanges changes with the server whenever it can.

## Data model

A note is small:

```ts
interface Note {
  id: string
  title: string
  body: string
  tags: string[]
  createdAt: string
  updatedAt: string
  deleted: boolean
}
```

Notes are never deleted outright; `deleted` is a tombstone. Without tombstones, a device that was offline during a deletion would happily sync the note back into existence.

### Changes, not snapshots

Instead of storing only the current state of each note, every edit is recorded as a change:

```ts
interface Change {
  id: string
  noteId: string
  deviceId: string
  counter: number
  field: 'title' | 'body' | 'tags' | 'deleted'
  value: unknown
  timestamp: string
}
```

The current state of a note is the result of applying its changes in order. Storing changes has three benefits: sync only needs to exchange changes the other side has not seen, history comes for free, and merging becomes a matter of ordering rather than guessing.

## Merging concurrent edits

The interesting part of any sync system is what happens when two devices edit the same thing while disconnected. There are two levels to get right.

### Fields: last writer wins, deterministically

For short fields such as the title, tags and the deleted flag, the latest change wins. "Latest" must be decided the same way on every device, even with skewed clocks, so changes are ordered by a hybrid logical clock: a timestamp combined with a counter and the device id as a final tie-breaker. Every device that sees the same set of changes arrives at the same result, without coordination.

### Text: a sequence CRDT

Last-writer-wins is wrong for the body of a note. If you add a paragraph on your phone and fix a typo on your laptop, you want both. For text, the body is stored as a sequence CRDT (a conflict-free replicated data type), where every character has a stable identity and insertions and deletions from different devices can be merged in any order with the same result.

Writing a sequence CRDT from scratch is a project of its own. The plan is to use an established library (Automerge and Yjs are the two mature options) for the body field only, and keep the simpler last-writer-wins scheme for everything else.

| Field     | Merge strategy             | Reason                               |
| --------- | -------------------------- | ------------------------------------ |
| `title`   | Last writer wins (HLC)     | Short; concurrent edits are rare     |
| `tags`    | Add-wins set               | Adding a tag on two devices keeps both |
| `deleted` | Last writer wins (HLC)     | A later restore beats an earlier delete |
| `body`    | Sequence CRDT              | Concurrent edits must both survive   |

## Storage on the device

IndexedDB is the only browser storage with enough capacity and transactional writes for this job. `localStorage` is synchronous, limited to a few megabytes and string-only. The local database has three object stores:

- **notes**: the materialised current state, indexed by `updatedAt` and tag, for fast listing and search.
- **changes**: the append-only log, indexed by note and by device counter.
- **sync**: per-peer bookmarks recording which changes have been sent and received.

Writes update `changes` and `notes` in one transaction, so the materialised view can never disagree with the log. The app also requests persistent storage from the browser, so the operating system does not evict the database under storage pressure.

## Sync protocol

Sync is a simple exchange of missing changes:

1. The device sends the highest counter it has seen from each device (a version vector).
2. The server replies with every change the device is missing and the counters it is missing from this device.
3. The device uploads those changes.
4. Both sides store the new changes and advance their bookmarks.

The server never needs to understand a note. It stores changes per user and relays them, which means it can store encrypted payloads it cannot read. A WebSocket keeps devices up to date while online; on reconnect, the same exchange catches up after any amount of time offline.

## Encryption

With end-to-end encryption enabled, each change's payload is encrypted on the device with a key derived from a passphrase that never leaves the user's devices. The server sees note ids, device ids, counters and ciphertext. The trade-off is explicit: if the passphrase is lost, the server cannot help recover the notes. The app makes that clear before encryption is turned on.

## The user interface

The UI is deliberately plain: a list of notes on the left, the editor on the right, a search box above both. Three details carry most of the "local-first feel":

- **No save button.** Every keystroke is persisted locally within a few milliseconds, debounced into one change per pause in typing.
- **Sync status is quiet.** A small indicator shows "Synced", "Offline, 12 changes waiting" or "Syncing…". It is never a modal and never blocks editing.
- **Search is local.** A full-text index is maintained on the device, so search works offline and returns results as you type.

## Progressive web app

A service worker caches the application shell, so the app starts with no network at all. A web app manifest gives it an icon, a name and a standalone window when installed. Updates to the app are downloaded in the background and applied on the next launch, with a small notice rather than a forced reload in the middle of writing.

## Compaction

An append-only log grows forever unless something trims it. Once every known device has acknowledged all changes up to a certain point, those changes are folded into a snapshot of each note and removed from the log. The sync bookmarks already record what each device has seen, so the safe point is simply the minimum across devices.

Devices that have not synced for a long time are the hard case. Holding the log open indefinitely for a phone in a drawer would defeat compaction, so devices silent for longer than a configurable period (for example ninety days) are marked stale. When a stale device returns, it downloads the snapshot and replays its own unsynced changes on top, rather than receiving the full history.

## Import and export

Lock-in is the opposite of what local-first promises, so getting data out is a first-class feature:

- **Export** writes every note as a Markdown file with a small front-matter block for tags and dates, zipped into a single download.
- **Import** reads the same format, plus plain text files, creating new notes with fresh ids so imports never collide with existing data.
- Exports work offline, because everything needed is already on the device.

A user who decides to leave can take every note with them in one click, in a format any editor understands.

## Testing strategy

Sync bugs are rare, hard to reproduce and destructive, so testing focuses on properties rather than examples:

- **Convergence**: generate random sequences of edits on two or three simulated devices, deliver the changes in random orders, and assert that every device ends with identical notes.
- **Idempotence**: delivering the same change twice has no effect.
- **Tombstones**: a deletion on one device survives a sync from a device that was offline during the deletion.
- **Clock skew**: devices with clocks hours apart still converge to the same ordering.
- **Crash safety**: interrupting a write transaction leaves the log and the materialised view consistent.

Property-based testing tools generate thousands of these scenarios per run, which finds the edge cases hand-written tests miss.

## Risks

| Risk                                                     | Mitigation                                             |
| -------------------------------------------------------- | ------------------------------------------------------ |
| Browser evicts IndexedDB under storage pressure          | Request persistent storage; sync as backup             |
| Change log grows without bound                           | Periodic compaction into snapshots once all devices have seen them |
| CRDT library becomes unmaintained                        | Body field is isolated behind one interface            |
| Lost passphrase with encryption on                       | Clear warning; optional recovery key printed at setup  |
| Schema changes break old devices                         | Versioned change format; old devices ignore unknown fields |

## Open questions

Some decisions are deliberately left open until the first milestones produce real data:

- **Which CRDT library?** Automerge keeps full history and has a clean document model; Yjs is smaller and faster for text-heavy workloads. A benchmark with realistic note sizes (a few kilobytes, edited in bursts) will decide.
- **How much history to show?** The change log makes a per-note timeline possible. Whether users want it, or whether it just adds clutter, is a product question to answer with a prototype.
- **Sharing between people.** The data model supports multiple writers, but permissions, invitations and encryption keys shared between users are a substantial design of their own.
- **Search across devices.** Each device indexes its own notes, which is fine while every device holds every note. If large archives ever stay server-side only, search would need a different approach that respects encryption.

Writing these down keeps the first version small: anything on this list is explicitly out of scope until it has an answer.

**token-forge** turns one JSON file of design tokens into a Tailwind CSS v4 theme, with light and dark values side by side, a contrast report that fails the build when a colour pair becomes unreadable, and a lint that refuses token names Tailwind would misinterpret. It is the tool I wished I had while building this site's token-only design system.

## The problem

A hand-written Tailwind v4 theme is just CSS, and that is both its strength and its weakness. It is easy to edit, but nothing checks it:

- A designer changes a colour, and the dark-theme value is forgotten.
- A new text colour is added and nobody checks its contrast against the backgrounds it will sit on.
- A token is renamed in the theme but not in the components, and the class silently stops producing CSS.
- A spacing token is given a name that collides with a Tailwind keyword and breaks an unrelated utility.

The last one happened on this site: a token called `--spacing-grid` made Tailwind generate `.inline-grid { inline-size: … }`, which overrode `display: inline-grid` and stretched every round avatar on the page. The theme compiled without a warning.

Each of these is a mistake a tool can catch, if the tokens are described as data instead of as CSS.

## Goals

| Goal                     | Meaning                                                          |
| ------------------------ | ---------------------------------------------------------------- |
| One source               | Tokens defined once, in JSON, with both themes next to each other |
| Faithful output          | Generates exactly the CSS a careful human would write by hand     |
| Contrast as a test       | Declared colour pairs are checked in both themes; failures fail the build |
| Safe names               | Names that collide with Tailwind utilities are rejected           |
| Usage check              | Optional scan of source files for classes that reference unknown tokens |
| No runtime               | Build-time only; the site ships plain CSS                         |

## Input format

Tokens are grouped by Tailwind namespace. Colours carry a light and a dark value; everything else can be a single value or a themed pair:

```json
{
  "color": {
    "canvas": {"light": "#f4f6f8", "dark": "#22272e"},
    "surface": {"light": "#fafbfc", "dark": "#272d35"},
    "fg": {"light": "#2b3137", "dark": "#adbac7"},
    "fg-muted": {"light": "#59636e", "dark": "#8b98a5"},
    "primary": {"light": "#1d4ed8", "dark": "#7aa2f7"},
    "primary-solid": {"light": "#12357f", "dark": "#1b3a8a"},
    "cover-fg": "#ffffff"
  },
  "radius": {"xs": "2px", "sm": "4px", "md": "6px", "full": "9999px"},
  "container": {
    "page": "108rem",
    "reading": "75ch",
    "dock": "min(24rem, calc(100vw - 2rem))"
  },
  "spacing": {
    "nav": "3.5rem",
    "band": "clamp(8.5rem, 16vh, 10rem)",
    "band-cell": "3rem"
  },
  "text": {
    "sm": {"size": "0.875rem", "lineHeight": "1.375rem"},
    "reading": {"size": "1.0625rem", "lineHeight": "1.875rem"}
  }
}
```

Each token may also carry a `description`, which becomes a CSS comment in the output and a row in the generated documentation.

### Contrast pairs

Pairs are declared explicitly, because only the combinations you actually use matter:

```json
{
  "contrast": [
    {"fg": "fg", "bg": "canvas", "min": 4.5},
    {"fg": "fg-muted", "bg": "canvas", "min": 4.5},
    {"fg": "primary", "bg": "surface", "min": 4.5},
    {"fg": "cover-fg", "bg": "primary-solid", "min": 4.5}
  ]
}
```

`min` follows WCAG: 4.5 for normal text, 3 for large text and essential interface elements.

## Output

The generator produces the theme block, the dark overrides and, optionally, the namespace resets:

```css
@theme {
  --color-*: initial;
  --radius-*: initial;
  --container-*: initial;

  --color-canvas: #f4f6f8;
  --color-fg: #2b3137;
  --color-primary: #1d4ed8;
  --color-cover-fg: #ffffff;

  --radius-sm: 4px;
  --container-page: 108rem;
  --spacing-band: clamp(8.5rem, 16vh, 10rem);

  --text-reading: 1.0625rem;
  --text-reading--line-height: 1.875rem;
}

:root[data-theme='dark'] {
  --color-canvas: #22272e;
  --color-fg: #adbac7;
  --color-primary: #7aa2f7;
}
```

Tokens with a single value (like `cover-fg`) appear only in `@theme`. The dark block contains only what changes, which keeps it short and easy to review.

The output is deterministic: tokens are emitted in input order within each namespace, and namespaces in a fixed order. Running the generator twice produces identical files, so diffs show only real changes.

## The contrast report

For each declared pair the tool resolves both colours in both themes, computes the WCAG relative luminance ratio and prints a table:

```text
Pair                         Light     Dark      Min   Result
fg on canvas                 12.14:1   7.60:1    4.5   pass
fg-muted on canvas            5.64:1   5.10:1    4.5   pass
primary on surface            6.47:1   5.51:1    4.5   pass
cover-fg on primary-solid    11.40:1  10.40:1    4.5   pass
```

These numbers are the real values for this site's tokens. A failing pair exits with code `1`, so the check belongs in CI next to linting. For a failing pair the report also suggests the nearest lightness adjustment that would pass, which turns "this is unreadable" into "change this hex to that hex".

Colours with alpha (such as `rgb(86 126 230 / 0.2)`) are composited over their declared background before measuring, because transparency changes the effective contrast.

## Name safety

Tailwind derives utility names from token names, and some namespaces generate more utilities than people expect. A spacing token creates height, width, padding, margin, inset and gap utilities, but also `inline-*` and `block-*` sizing utilities. A container token creates `max-w-*`, `w-*` and `basis-*`.

token-forge keeps a list of Tailwind keywords that would collide (`grid`, `flex`, `block`, `table`, `hidden`, `contents`, `full`, `screen`, `auto` and others) and rejects any token whose generated utility would shadow one of them:

```text
error  spacing.grid: generates "inline-grid", which overrides the
       display utility of the same name. Choose a two-word name such
       as "band-cell".
```

The rule is cheap and would have saved an evening of debugging stretched avatars.

## Usage check

With `--scan "src/**/*.tsx"`, the tool reads source files, extracts class names (including inside `cn()` calls and template literals with literal segments) and reports:

- classes that reference a token which does not exist (`text-fg-mutd`);
- tokens that are never used, as candidates for removal;
- raw hex colours and pixel arbitrary values in components, which the token system is meant to replace.

The scan is heuristic by nature, so it reports warnings rather than errors.

## Architecture

```text
tokens.json ─► parse & validate ─► resolve themes ─┬─► emit CSS ─► main.css (generated block)
                (schema, names)    (light/dark)      ├─► contrast report
                                                     ├─► docs table (Markdown)
                                                     └─► usage scan (optional)
```

The core is a pure function from a validated token object to strings. That makes snapshot tests trivial: a fixture JSON file and its expected CSS, report and documentation.

### Coexisting with hand-written CSS

The generated output goes between two marker comments in `main.css`. Everything outside the markers (the base layer, keyframes, third-party rules such as the Shiki theme switch) stays hand-written. Running the generator replaces only the marked block, so adopting the tool does not mean giving up control of the rest of the stylesheet.

## Generated documentation

A token system is only useful if people can find the tokens. Alongside the CSS, token-forge writes a Markdown reference: one table per namespace with the token name, the utilities it produces, the light and dark values, a colour swatch and the description from the JSON file.

```text
| Token          | Utilities                   | Light    | Dark     | Description       |
| -------------- | --------------------------- | -------- | -------- | ----------------- |
| fg-muted       | text-fg-muted, …            | #59636e  | #8b98a5  | Secondary text    |
| primary-solid  | bg-primary-solid, …         | #12357f  | #1b3a8a  | Buttons and bands |
```

The reference is regenerated on every run, so it can never fall behind the theme. On this site it would replace the hand-maintained token table in the design-system guide.

## Command line

```bash
npx token-forge build tokens.json --out src/main.css
npx token-forge check tokens.json --scan "src/**/*.tsx"
npx token-forge docs tokens.json --out docs/tokens.md
```

| Command  | What it does                                                    | Exit code on problems |
| -------- | --------------------------------------------------------------- | --------------------- |
| `build`  | Validate, then write the generated block into the stylesheet    | 1 on any error        |
| `check`  | Validate, contrast report, optional usage scan; writes nothing  | 1 on any error        |
| `docs`   | Write the Markdown reference                                    | 1 on any error        |

`check` is the command for CI: it is read-only, fast and fails on the same rules as `build`. A pre-commit hook can run `build` so the generated block is always up to date in the repository.

## Working with designers

Design tools increasingly export tokens as JSON, often in the format proposed by the W3C Design Tokens Community Group. token-forge accepts that format through an import step that maps its `$value` and `$type` fields onto the namespaces above. The intended workflow:

1. A designer changes a colour in the design tool and exports tokens.
2. The import step converts the export and opens a pull request.
3. CI runs `check`. If a contrast pair fails, the designer sees the report on the pull request, with a suggested value that would pass.
4. Once green, the change merges and the site picks up the new theme on the next build.

Nobody hand-copies hex values, and accessibility problems are caught before review rather than after release.

## More than two themes

Light and dark are the common case, but the format allows any number of named themes, for example a high-contrast theme:

```json
{
  "themes": ["light", "dark", "contrast"],
  "color": {
    "fg": {"light": "#2b3137", "dark": "#adbac7", "contrast": "#000000"}
  }
}
```

Each extra theme becomes another `:root[data-theme='…']` block, and every contrast pair is checked in every theme. A theme that omits a token falls back to the light value, with a warning so the omission is deliberate.

## How it compares

Style Dictionary, from Amazon, is the established tool for transforming tokens into many platforms (CSS, iOS, Android). It is powerful and general. token-forge is deliberately narrow: one input format, one output target (Tailwind v4), and opinions about contrast and naming that a general tool cannot have. If you need tokens on several platforms, use Style Dictionary and add contrast checks to its pipeline. If you have one Tailwind site and want guard rails, a narrow tool is simpler to adopt and to trust.

## Validation rules

| Rule                                      | Severity |
| ----------------------------------------- | -------- |
| Unknown namespace                         | Error    |
| Colour without a dark value (unless marked theme-independent) | Error |
| Invalid CSS value (parsed with a CSS value parser) | Error |
| Name collides with a Tailwind keyword     | Error    |
| Contrast pair below its minimum           | Error    |
| Token never used in scanned sources       | Warning  |
| Raw hex or pixel value in a component     | Warning  |

## Testing strategy

- **Parser tests**: valid and invalid inputs for every namespace, including themed and plain values.
- **Emitter snapshots**: fixture tokens to expected CSS, byte for byte.
- **Contrast tests**: known pairs with published ratios (black on white is 21:1), alpha compositing, rounding at the threshold.
- **Collision tests**: every keyword in the list rejected in every namespace that would generate it.
- **Round trip**: generating this site's theme from JSON reproduces the current `main.css` token section exactly.

That last test is the acceptance criterion. The tool is done when it can take over this site's theme without changing a single rendered pixel.

## Design decisions

- **JSON, not a new language.** Tokens are data. JSON is boring, diffable and readable by any other tool, including a design tool export.
- **Explicit contrast pairs.** Checking every colour against every other would produce hundreds of irrelevant failures. Only real combinations matter.
- **Generate CSS, not a Tailwind plugin.** Tailwind v4's configuration is CSS. Generating CSS keeps the output inspectable and the tool independent of Tailwind's internals.

NASA writes software that cannot be patched once it leaves Earth, so its documentation rules are thorough to the point of sounding absurd for a side project. Read past the acronyms, though, and the core ideas are simple: write down what the system must do, how it is built, where its boundaries are, how you will prove it works and what could go wrong. Those questions matter just as much for a one-person website. This article explains the NASA document set, shows how I scaled it down for this site, and argues that the result is less paperwork than it sounds, and more useful than a README.

## Why bother?

Small projects usually have two kinds of documentation: a README that was accurate on the day it was written, and the code. That works until one of these happens:

- You come back after six months and cannot remember why a dependency is pinned.
- An AI assistant or a new contributor changes behaviour you depended on, because nothing said it was intentional.
- A "quick fix" breaks a feature nobody tested, because nobody wrote down that the feature existed.

Each of those is a missing record: a decision, a requirement or a test. The NASA approach is a checklist of records worth keeping. You do not need to keep them at NASA's level of detail to get most of the benefit.

## The sources

NASA's software rules come from a handful of public documents:

| Document          | What it covers                                               |
| ----------------- | ------------------------------------------------------------ |
| NPR 7150.2        | Software engineering requirements for every NASA project     |
| NASA-HDBK-2203    | Handbook explaining how to meet NPR 7150.2, with document outlines |
| NASA-STD-8739.8   | Software assurance and software safety                       |
| "Power of Ten"    | Ten coding rules for safety-critical C, by Gerard Holzmann at JPL |

NPR 7150.2 is the rulebook. It lists numbered requirements (they are called SWE-001, SWE-002 and so on) such as "the project shall develop a software management plan" or "the project shall perform bidirectional traceability between requirements and tests". The handbook then explains, for each one, what a good document looks like.

## Classification: how much rigour do you need?

The most useful idea in NPR 7150.2 is that rigour depends on consequences. Every project gets a **software class**:

| Class | Example                                          |
| ----- | ------------------------------------------------ |
| A     | Human-rated space flight software                |
| B     | Non-human space flight, critical ground systems  |
| C     | Mission support software                         |
| D     | Analysis and simulation tools                    |
| E     | Design concept and research software             |
| F     | General-purpose IT and business software         |

A requirement that applies fully to Class A may be optional for Class F. A personal website is Class F at most: if it fails, a page does not render. That classification is not an excuse to skip documentation; it is a licence to keep each document short.

Write the classification down. It answers every future "do we really need X?" question in one line.

## The core document set

Out of everything NASA asks for, these documents carry most of the value:

1. **Software Management Plan (SMP)**: scope, classification, roles, lifecycle, milestones, standards.
2. **Software Requirements Specification (SRS)**: what the system must do, as numbered, testable "shall" statements.
3. **Software Design Description (SDD)**: how it is built: layers, modules, data flow, state, and the reasons for each decision.
4. **Interface Control Document (ICD)**: every boundary: types, APIs, storage formats, third-party services, file formats.
5. **Software Test Plan (STP)**: levels, tools, environments, entry and exit criteria.
6. **Software Test Procedures**: the individual test designs, step by step.
7. **Requirements Traceability Matrix (RTM)**: a table linking each requirement to design, code, tests and status.
8. **Software Version Description (SVD)**: what is in this release, how to build it, known issues.

Add three living records: a **risk register**, **architecture decision records** and a **coding standard**. For this site that is thirteen Markdown files, most of them a few pages long.

## Requirements you can test

A requirement that cannot be verified is a wish. Good requirements follow a pattern: an ID, the word "shall", one condition and one measurable outcome.

| Weak                            | Strong                                                                                       |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| The site should be fast.        | **SRS-PERF-02** Largest Contentful Paint should be under 2.5 s on a mid-range phone over 4G. |
| Favorites should be saved.      | **SRS-ART-12** Like and save shall toggle per article and persist in `localStorage`.          |
| Search should be good.          | **SRS-SRCH-03** Every query term shall match a result; title prefix matches rank first.      |
| The layout should look nice.    | **SRS-CMP-02** No route shall scroll horizontally at widths from 360 px to 3840 px.          |

"Shall" means mandatory, "should" means recommended and "may" means optional. That vocabulary sounds pedantic until you need to decide whether a failing check blocks a release.

Group requirements by area with a short prefix: navigation, articles, search, player, chat, accessibility, security, maintainability. This site has around a hundred of them, and writing them took an afternoon, mostly by describing what the code already did.

### Record where each requirement came from

Add a source column. On this site most requirements trace back to a specific request ("make the navbar transparent over the header") or to a standard (WCAG for contrast). When someone later asks "why does it do that?", the answer is one lookup away.

## Decide how each requirement is verified

NASA uses four verification methods, and every requirement gets at least one:

- **Test (T)**: run it and measure, automatically or by hand.
- **Analysis (A)**: prove it from calculation or modelling.
- **Inspection (I)**: examine code, configuration or output.
- **Demonstration (D)**: show that it works, without detailed measurement.

This is where the approach earns its keep. "No semicolons in TypeScript" is verified by inspection, automated by a lint rule. "Colour contrast meets WCAG AA" is verified by analysis: compute the ratio for every pair of colour tokens. "Music keeps playing across pages" is a demonstration until an end-to-end test exists.

Doing the analysis for contrast on this site found a real defect: the faintest text colour in dark mode measured 2.90:1 against the page background, just under the 3:1 minimum. No visual review had caught it. Writing the requirement down and deciding how to verify it did.

## Test designs, not just tests

The test plan says *how* testing happens: levels (static analysis, unit, component, end to end, manual), tools, environments and criteria. The test procedures say *what* is tested, case by case:

```text
TC-CHAT-03  Title rule (SRS-CHAT-05)
  First visitor message of 40 characters  → title is the same 40 characters
  First visitor message of 41 characters  → first 40, trimmed, then "…"
  Second visitor message                  → title unchanged
```

Writing test designs before the tests exist is useful in itself. It forces boundary values into the open (why 40?), and it gives you a ready-made backlog when you do set up a test runner. Each design names the requirement it verifies, so the matrix stays complete.

Be honest about status. On this site most automated tests are designed but not yet implemented, and the documents say exactly that. A test plan that pretends to coverage you do not have is worse than none.

## Keep a traceability matrix

The matrix is what turns a pile of documents into a system. One row per requirement:

| Requirement | Design      | Code                         | Test               | Status   |
| ----------- | ----------- | ---------------------------- | ------------------ | -------- |
| SRS-ART-12  | SDD §4.4    | `ArticleInteractionStore`    | TC-ART-03          | Designed |
| SRS-LAY-04  | SDD §4.5    | `HeaderBand`                 | TC-E2E-04          | Pass     |
| SRS-A11Y-03 | SDD §4.9    | colour tokens                | TC-MAN-03          | Fail     |

Traceability works in both directions. Forward: every requirement has a design element and a test. Backward: every test points to a requirement, so you never maintain a test nobody can justify. When a requirement changes, the row tells you which design section and which tests to revisit.

A useful habit is to count statuses at each release. "58 pass, 42 designed, 4 open, 1 fail" is a far more honest progress report than "tests are green".

## Interfaces deserve their own document

Most bugs live at boundaries, and boundaries are where implicit assumptions hide. The interface control document lists every one:

- Internal contracts: the service interface, the shape of each context value, the search source contract.
- Content formats: which fields an article needs, which are ISO dates, which are minutes.
- Browser storage: every key, its schema and who writes it.
- Third parties: which Spotify URLs load, when, and with what parameters.
- Build interfaces: what each npm script guarantees.

Writing down the storage keys turned out to be the most valuable part on this site. It made it obvious that the privacy policy was missing one of them.

## Record decisions as they happen

Every non-obvious choice gets a short architecture decision record: context, decision, consequences. A few lines each:

```text
ADR-005  Google TypeScript Style (gts) as "checkstyle"
Context:  Owner asked for the TypeScript equivalent of Java Checkstyle.
Decision: gts 7 with ESLint 9 and Prettier, one npm script.
Consequence: ESLint is pinned to v9 until gts supports v10.
```

That last line is the one future you will thank you for. Without it, someone eventually "upgrades" ESLint and spends an evening working out why the config broke.

## Risks are not pessimism

A risk register lists what might go wrong, how likely and how bad it would be, and what you are doing about it. Score likelihood and impact from 1 to 5 and multiply. Anything at 15 or above blocks a release.

On this site, the highest-scoring risk is that resume requests are kept only in the browser tab and are lost on reload. It is fine for development and unacceptable for a public launch. Writing it down with a score means it cannot be forgotten in the excitement of shipping.

## Adapt the Power of Ten

Holzmann's rules target safety-critical C, but several translate directly to TypeScript:

| Rule (C)                                   | TypeScript adaptation                                         |
| ------------------------------------------ | ------------------------------------------------------------- |
| Simple control flow, no recursion          | Early returns, no recursion over external data                |
| Fixed bounds on loops                      | Bound loops over stored or fetched data (`slice(0, limit)`)   |
| Functions fit on one page                  | Keep functions and components small; extract when they grow   |
| Check return values                        | Handle `undefined` from lookups; never leave a promise floating |
| Smallest possible scope                    | `const` by default; state in the lowest component that needs it |
| All warnings on, zero warnings             | Strict lint and type checks; the build must be clean          |

Several of these can be enforced by tools. `no-floating-promises` covers "check return values" for async code. The rest go into the coding standard and the review checklist.

## Assurance: a checklist, not a department

NASA has whole organisations for software assurance. A one-person project needs two checklists: one for every change and one for every release. Mine include items like:

- Lint, format, license and type checks pass.
- New colours have both a light and a dark value.
- External links opening in a new tab use `noopener`.
- The privacy policy matches the storage keys listed in the interface document.
- Documents affected by the change are updated in the same commit.

A short lightweight failure-mode table is also worth having. For each component, ask what happens when it fails: storage unavailable, third-party script blocked, a lazy chunk failing to download. Several "none yet" answers on this site became entries in the risk register.

## Keep it alive

Documentation that is not updated is worse than none, because it is confidently wrong. Three rules keep this set honest:

1. **Same change, same commit.** A pull request that changes behaviour updates the requirement, design section, test design and matrix row with it.
2. **Status words mean something.** "Pass" needs evidence. "Designed" is fine and honest. Never write "Pass" for something you did not check.
3. **Review at release.** The version description gets a short verification summary: what was checked, what failed, what is known to be missing.

## What it cost

For this site, the full set took roughly a day to write, most of it describing what already existed. Keeping it current adds a few minutes to each change. In return it has already found a contrast failure, a gap in the privacy policy and a high-scoring risk that would otherwise have gone live.

</Callout>

## Getting started on your own project

You do not need all thirteen documents on day one. A sensible order:

1. Write the classification and goals in one page.
2. List requirements for the features that exist, with verification methods.
3. Record the three decisions you are most likely to forget.
4. Start a risk register with whatever currently worries you.
5. Add the matrix once you have tests to point at.

Each step is useful on its own, and each one makes the next change a little safer.

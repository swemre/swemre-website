Not every feature needs a server. Views, likes and favorites can live in the browser until you genuinely need to share them across devices or aggregate them across visitors. This article builds a small, robust interaction store on top of `localStorage` and React's `useSyncExternalStore`: about seventy lines of code that survive private browsing, corrupted data, React StrictMode and multiple open tabs.

## The problem

Every article on this site has three pieces of visitor state:

- **Views**: how many times this browser has opened the article.
- **Liked**: a heart toggle.
- **Saved**: a bookmark toggle, used by the "Saved only" filter on the articles page.

The obvious solution is a backend with a table of interactions. That brings authentication questions, a database, an API, rate limiting and a privacy policy that has to explain all of it. For a personal site, none of that pays for itself on day one. What visitors actually need is for their own likes and bookmarks to stick around, and that is exactly what browser storage is for.

## Two kinds of data, two homes

The first design decision is to separate data by who owns it and how often it changes:

| Data                            | Where it lives         | Why                                               |
| ------------------------------- | ---------------------- | ------------------------------------------------- |
| Title, slug, summary, tags      | Typed array in the repo | Shipped with the build; never changes at runtime |
| Article body                    | MDX file per article    | Compiled and code-split at build time            |
| Views, likes, favorites         | `localStorage`          | Per visitor, written on interaction              |

The two halves meet through one field: the article `id`. That id is permanent. If it ever changed, every visitor's likes for that article would silently disappear, because they are stored under the old key. Slugs can change (with a redirect), titles can change, but ids cannot.

## Designing the storage format

All interactions live under a single key as one JSON object:

```json
{
  "a1f3c9d2": {"views": 3, "liked": true, "favorited": false},
  "b7e20a54": {
    "views": 1,
    "liked": false,
    "favorited": true,
    "lastViewedAt": "2026-10-14T18:22:05.120Z"
  }
}
```

Why one key instead of one key per article?

- **Atomic reads.** The articles index needs every article's state at once to filter by "saved". One `getItem` and one `JSON.parse` is cheaper than dozens.
- **Easy reset.** Clearing a single key wipes all interaction data.
- **One place to version.** If the shape ever changes, one migration handles it.

The key itself is namespaced: `swemre:article-interactions`. Every key this site writes starts with `swemre:`, so it never collides with anything else running on the same origin and is easy to find in DevTools.

## Why `useSyncExternalStore`?

The naive approach is a `useState` initialised from storage plus a `useEffect` that writes back. It works for one component, but breaks down quickly:

- Two components showing the same article's like button get out of sync.
- A toggle in one tab is invisible in another tab.
- Every component re-reads and re-parses storage on mount.

React 18 introduced `useSyncExternalStore` for exactly this case: state that lives **outside** React but must be read consistently **inside** it. You give it two functions:

1. `subscribe(callback)`: register a listener and return an unsubscribe function.
2. `getSnapshot()`: return the current value. It must return the same reference when nothing has changed.

React calls `getSnapshot` during render, and re-renders subscribers whenever a listener fires and the snapshot reference changes. There is no tearing during concurrent rendering, and no effect timing to think about.

## The store

Here is the store this site uses, slightly condensed. It has four parts: a cache, a reader, a writer and the public API.

```ts
const KEY = 'swemre:article-interactions'
const EMPTY: ArticleInteraction = {views: 0, liked: false, favorited: false}

const listeners = new Set<() => void>()
let cache: ArticleInteractionState | null = null

function read(): ArticleInteractionState {
  if (cache) return cache
  try {
    cache = JSON.parse(
      localStorage.getItem(KEY) ?? '{}',
    ) as ArticleInteractionState
  } catch {
    cache = {}
  }
  return cache
}
```

The cache is what makes `getSnapshot` cheap and stable. Storage is parsed once; afterwards `read()` returns the same object until a write replaces it. That stability matters: if `getSnapshot` returned a freshly parsed object every time, React would see a "new" value on every render and loop.

The `try`/`catch` matters just as much. `JSON.parse` throws on invalid input, and `localStorage.getItem` itself can throw in some browsers when storage is disabled. Either way, the store falls back to an empty object and the page keeps working.

### Writing

```ts
function write(next: ArticleInteractionState) {
  cache = next
  try {
    localStorage.setItem(KEY, JSON.stringify(next))
  } catch {
    // Storage full or unavailable: keep in-memory state only.
  }
  listeners.forEach(listener => listener())
}

function update(
  id: string,
  patch: (current: ArticleInteraction) => Partial<ArticleInteraction>,
) {
  const state = read()
  const current = state[id] ?? EMPTY
  write({...state, [id]: {...current, ...patch(current)}})
}
```

Three properties are deliberate:

1. **Writes are immutable.** `update` builds a new top-level object and a new entry. The old snapshot is never mutated, so React's reference comparison sees the change.
2. **The cache updates before storage.** If `setItem` throws (quota exceeded, Safari private mode in older versions), the in-memory state is still correct for the rest of the session.
3. **Listeners run last**, after both the cache and storage are up to date.

### The public API

```ts
export const articleInteractionStore = {
  subscribe(callback: () => void) {
    listeners.add(callback)
    const onStorage = (event: StorageEvent) => {
      if (event.key === KEY) {
        cache = null
        callback()
      }
    }
    window.addEventListener('storage', onStorage)
    return () => {
      listeners.delete(callback)
      window.removeEventListener('storage', onStorage)
    }
  },
  readAll: read,
  readOne: (id: string): ArticleInteraction => read()[id] ?? EMPTY,
  toggleLike: (id: string) => update(id, c => ({liked: !c.liked})),
  toggleFavorite: (id: string) => update(id, c => ({favorited: !c.favorited})),
  registerView: (id: string) =>
    update(id, c => ({
      views: c.views + 1,
      lastViewedAt: new Date().toISOString(),
    })),
}
```

Note that `readOne` returns the shared `EMPTY` constant for unknown articles instead of a new object. Returning `{views: 0, ...}` inline would create a new reference on every call and trigger the same infinite re-render problem described above.

## Syncing across tabs

Browsers fire a `storage` event in **other** tabs of the same origin whenever one tab writes to `localStorage`. The store listens for it, throws away its cache (the other tab's data is newer) and notifies subscribers. The result: like an article in one tab and the heart fills in the other tab immediately, with no polling and no BroadcastChannel.

The event does not fire in the tab that made the change, which is why local writes notify listeners directly.

## The hooks

Components never touch the store's internals. Two tiny hooks wrap it:

```ts
export const useArticleInteraction = (id: string): ArticleInteraction =>
  useSyncExternalStore(articleInteractionStore.subscribe, () =>
    articleInteractionStore.readOne(id),
  )

export const useAllArticleInteractions = (): ArticleInteractionState =>
  useSyncExternalStore(
    articleInteractionStore.subscribe,
    articleInteractionStore.readAll,
  )
```

And a component reads and writes with no ceremony:

```tsx
export function ArticleActions({id}: {id: string}) {
  const {liked, favorited, views} = useArticleInteraction(id)
  return (
    <button
      type="button"
      aria-pressed={liked}
      onClick={() => articleInteractionStore.toggleLike(id)}
    >
      {liked ? 'Liked' : 'Like'} · {views} views
    </button>
  )
}
```

The `aria-pressed` attribute is worth calling out: a toggle button should announce its state to screen readers, not just change colour.

## Counting views correctly

A view should be counted once per visit. In development, React StrictMode intentionally runs effects twice to surface bugs, which would double every count. A ref guard fixes it:

```tsx
const counted = useRef<string | null>(null)

useEffect(() => {
  if (!id || counted.current === id) return
  counted.current = id
  articleInteractionStore.registerView(id)
}, [id])
```

The ref survives StrictMode's simulated unmount and remount, so the second run sees the id and returns early. Because the guard compares ids rather than using a boolean, navigating from one article to another still counts the new one.

## Filtering by saved articles

The articles index uses `useAllArticleInteractions` to build its "Saved only" filter:

```ts
const shown = all.filter(
  article =>
    (!activeTag || article.tags.includes(activeTag)) &&
    (!onlySaved || interactions[article.id]?.favorited),
)
```

Because the hook subscribes to the same store, saving an article in another tab updates the filtered list here without a reload.

## Failure modes and how each is handled

| Failure                                  | What happens                                               |
| ---------------------------------------- | ---------------------------------------------------------- |
| `localStorage` disabled or throws        | Reads fall back to `{}`, writes stay in memory             |
| Quota exceeded                           | Same as above for the failing write                        |
| Invalid JSON (someone edited DevTools)   | Treated as empty; the next write replaces it               |
| Valid JSON with an unexpected shape      | Missing fields fall back to `EMPTY` per article            |
| Another tab writes                       | Cache invalidated, subscribers re-render                   |
| StrictMode double effects                | Ref guard counts one view                                  |

A stricter version would validate the parsed object field by field. For a feature where the worst case is a wrong view count on one visitor's machine, defensive defaults are enough.

## Versioning the stored shape

Stored data outlives deploys. A visitor who liked an article in January still has that JSON in March, after you have changed the code three times. Treat the stored shape as a public interface.

Adding an optional field, as `lastViewedAt` was added here, is always safe: old entries simply lack it, and readers treat it as absent. Renaming or removing a field is not. If you ever need to, store a version number alongside the data and migrate on read:

```ts
interface StoredInteractions {
  version: 2
  articles: ArticleInteractionState
}

function migrate(raw: unknown): ArticleInteractionState {
  if (raw && typeof raw === 'object' && 'version' in raw) {
    return (raw as StoredInteractions).articles
  }
  return (raw ?? {}) as ArticleInteractionState
}
```

The migration runs inside `read()`, and the next write saves the new shape. Visitors never notice, and you never need a "clear your browser data" note.

It also helps to keep every storage key, its schema and its owner in one written list. On this site that list lives in the interface control document, next to the service contracts. It is the first place to look when you change a shape, and it is the source for the privacy policy.

## Privacy

Local-first is also privacy-friendly by design. Nothing in this store leaves the device. There are no cookies and no identifiers, and the privacy policy can say so in one sentence: these values are stored in your browser, never sent anywhere, and you can delete them by clearing site data.

That changes the day you add a backend. Plan for it now by keeping all storage keys in one documented place, so the privacy policy and the code stay in step.

## Testing the store

The store is plain TypeScript with no React dependency, so it tests well in isolation:

- Toggling twice returns to the original state.
- `registerView` twice gives `views: 2` and sets `lastViewedAt`.
- A listener is called exactly once per write.
- Dispatching a `StorageEvent` with the store's key invalidates the cache; other keys are ignored.
- Seeding storage with `"oops"` returns `{}` without throwing.

Component tests then only need to check that buttons call the right store function and reflect `aria-pressed`.

## Moving to a backend later

Because components only call `toggleLike`, `toggleFavorite`, `registerView` and the two hooks, moving to a server is a change in one file. A reasonable path:

1. Keep `localStorage` as an optimistic cache so the UI stays instant.
2. Send each change to an API in the background, retrying when offline.
3. Fetch aggregate counts (total likes across visitors) separately; they are a different feature with different caching rules.

The visitor-facing behaviour does not change, and neither do the components.

## Summary

A local-first interaction store needs very little code: a namespaced key, a cached reader, an immutable writer, a listener set and the `storage` event. `useSyncExternalStore` connects it to React correctly, and a handful of `try`/`catch` blocks make it robust against everything browsers throw at it. Start there, ship the feature, and add a server only when you have a reason that a visitor would notice.

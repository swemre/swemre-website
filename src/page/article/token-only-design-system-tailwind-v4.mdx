Tailwind ships with hundreds of colours, shadows, sizes and radii. That is great for a prototype and quietly corrosive for a product: six months in, nobody knows which of `blue-600`, `blue-700` and `indigo-700` is "the" primary colour, and dark mode is a patchwork of `dark:` prefixes. This article shows how to wipe Tailwind v4's defaults and replace them with a small set of named tokens that the whole interface must use. The result is a design system that lives in one CSS file and that the compiler enforces for you.

## The idea in one sentence

If a value is not a token, the class for it does not exist.

That is the entire approach. Instead of a style guide that asks people to use the right colour, the build only knows the right colours. `bg-blue-600` produces nothing, so it cannot sneak into a pull request.

## Why tokens, and why semantic names?

A token is a named design decision: "the colour of muted text", "the radius of a card", "the height of the navbar". Components reference the name, never the value.

| Without tokens                         | With semantic tokens                      |
| -------------------------------------- | ----------------------------------------- |
| `text-gray-500`                        | `text-fg-muted`                           |
| `bg-white dark:bg-gray-900`            | `bg-surface`                              |
| `border-gray-200 dark:border-gray-700` | `border-border`                           |
| `bg-blue-700 hover:bg-blue-800`        | `bg-primary-solid hover:bg-primary-solid-hover` |
| `max-w-[1400px]`                       | `max-w-page`                              |
| `h-[152px]`                            | `h-embed`                                 |

Semantic names survive redesigns. If the brand colour moves from blue to green, `primary` is still `primary`, and not a single component changes. A name like `blue-700` would be a lie the day after.

## How Tailwind v4 reads a theme

Tailwind v4 moved configuration from JavaScript into CSS. The `@theme` block declares CSS custom properties, and each property name tells Tailwind which utilities to generate:

| Namespace       | Example token              | Utilities generated                              |
| --------------- | -------------------------- | ------------------------------------------------ |
| `--color-*`     | `--color-surface`          | `bg-surface`, `text-surface`, `border-surface`, `ring-surface`, `from-surface`, … |
| `--shadow-*`    | `--shadow-md`              | `shadow-md`                                      |
| `--radius-*`    | `--radius-sm`              | `rounded-sm`, `rounded-t-sm`, …                  |
| `--font-*`      | `--font-mono`              | `font-mono`                                      |
| `--text-*`      | `--text-reading`           | `text-reading` (with a paired line height)       |
| `--container-*` | `--container-page`         | `max-w-page`, `w-page`, `basis-page`             |
| `--spacing-*`   | `--spacing-nav`            | `h-nav`, `pt-nav`, `top-nav`, `mt-nav`, `inline-nav`, … |
| `--animate-*`   | `--animate-pop`            | `animate-pop`                                    |

Every token is also a real CSS variable at runtime. That is what makes theme switching cheap.

## Step 1: clear the defaults

Setting a namespace to `initial` removes every built-in value in it:

```css
@import 'tailwindcss';

@theme {
  --color-*: initial;
  --shadow-*: initial;
  --inset-shadow-*: initial;
  --drop-shadow-*: initial;
  --radius-*: initial;
  --font-*: initial;
  --text-*: initial;
  --container-*: initial;
}
```

After this block, `text-red-500`, `shadow-lg`, `rounded-xl` and `max-w-2xl` compile to nothing. The base spacing scale (`--spacing`, used by `p-4`, `gap-2`, `size-8`) is kept on purpose: it is a rhythm, not a design decision, and clearing it would make every padding an arbitrary value.

<Callout type="tip">
  Clear namespaces one at a time on an existing project. Each one you clear will break the classes that relied on it, and the broken classes are your migration list.
</Callout>

## Step 2: add semantic colour tokens

Group colours by role. This site uses six groups:

```css
@theme {
  /* surfaces */
  --color-canvas: #f4f6f8;
  --color-canvas-subtle: #eef1f4;
  --color-surface: #fafbfc;
  --color-surface-muted: #f0f3f6;
  --color-overlay: #fbfcfd;
  --color-inset: #eaeef2;

  /* text */
  --color-fg: #2b3137;
  --color-fg-strong: #1f2328;
  --color-fg-muted: #59636e;
  --color-fg-subtle: #818b98;
  --color-fg-on-emphasis: #ffffff;

  /* borders */
  --color-border: #d4dae0;
  --color-border-muted: #e2e7ec;
  --color-border-strong: #b4bec8;

  /* brand */
  --color-primary: #1d4ed8;
  --color-primary-muted: #e0e7fa;
  --color-primary-solid: #12357f;
  --color-primary-solid-hover: #1a46a6;

  /* status */
  --color-success: #1a7f37;
  --color-attention: #9a6700;
  --color-danger: #cf222e;
}
```

A few naming patterns make the set predictable:

- **`-muted`** is a quiet background version of a colour, used for badges and highlights.
- **`-solid`** is the filled version, used for primary buttons and bands.
- **`-strong` and `-subtle`** step text emphasis up and down from the default `fg`.
- **`on-emphasis`** is the text colour that goes on top of a solid fill.

## Step 3: dark mode as a variable swap

Because every utility reads a CSS variable, dark mode does not need `dark:` prefixes. Redefine the same variables under a theme attribute:

```css
:root[data-theme='dark'] {
  --color-canvas: #22272e;
  --color-surface: #272d35;
  --color-fg: #adbac7;
  --color-fg-muted: #8b98a5;
  --color-border: #444c56;
  --color-primary: #7aa2f7;
  --color-primary-solid: #1b3a8a;

  color-scheme: dark;
}
```

The theme switch sets `data-theme` on the `html` element, and every component updates in one paint. A tiny inline script in `index.html` sets the attribute before React loads, so dark-mode visitors never see a white flash.

Not every colour has to change. Tokens for content that sits on a fixed dark background, such as the text over the header band, keep the same value in both themes.

## Step 4: shadows, radii, fonts and text sizes

Shadows reference colour tokens, so they adapt to the theme too:

```css
@theme {
  --color-shadow: rgb(31 35 40 / 0.1);

  --shadow-xs: 0 1px 0 var(--color-shadow);
  --shadow-sm: 0 1px 2px var(--color-shadow);
  --shadow-md: 0 3px 6px var(--color-shadow), 0 1px 2px var(--color-shadow);

  --radius-xs: 2px;
  --radius-sm: 4px;
  --radius-md: 6px;
  --radius-full: 9999px;

  --font-sans: -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif;
  --font-mono: ui-monospace, SFMono-Regular, Menlo, Consolas, monospace;

  --text-sm: 0.875rem;
  --text-sm--line-height: 1.375rem;
  --text-reading: 1.0625rem;
  --text-reading--line-height: 1.875rem;
}
```

The `--text-*--line-height` companion is a Tailwind v4 convention: `text-reading` sets both the font size and its line height. Pairing them in the theme means nobody has to remember the right `leading-*` for each size.

Keeping only five radii (and making the small one the default) is what gives the site its crisp, documentation-like feel.

## Step 5: layout tokens

Widths and heights are design decisions too. When they are written into components as `max-w-[1400px]` or `h-[152px]`, they are impossible to find and tune. Make them tokens:

```css
@theme {
  --container-page: 108rem;
  --container-wide: 116rem;
  --container-reading: 75ch;
  --container-sidebar: clamp(14rem, 14vw, 19rem);
  --container-dock: min(24rem, calc(100vw - 2rem));

  --spacing-nav: 3.5rem;
  --spacing-band: clamp(8.5rem, 16vh, 10rem);
  --spacing-embed: 9.5rem;
}
```

Two things are worth noticing:

1. **Fluid values live in the token.** `clamp()` and `min()` belong in CSS, not in class names. A component writes `w-dock` and gets a panel that is 24rem wide on desktop and full width minus a gutter on a phone.
2. **Third-party constraints become named tokens.** Spotify's compact embed is 152 pixels tall. That number is now `--spacing-embed` with a comment explaining where it comes from.

Arbitrary values are still allowed for things Tailwind cannot name, such as grid templates, but they reference tokens:

```tsx
<div className="grid lg:grid-cols-[var(--container-sidebar)_minmax(0,1fr)]" />
```

### Measuring text in characters

The reading column deserves a special unit. Typographers have recommended roughly 45 to 75 characters per line for comfortable reading for a long time; shorter lines break the rhythm, longer ones make it hard to find the start of the next line. CSS has a unit for exactly this: `ch`, the width of the "0" glyph in the current font.

```css
@theme {
  --container-reading: 75ch;
}
```

A `max-w-reading` column now holds about 70 characters of body text, whatever the screen size. On a wide monitor the page gets more margin, not longer lines. Because the header block of each article (breadcrumbs, title, summary) lives in the same column, it lines up with the text beneath it.

There is one subtlety: `ch` is resolved against the font size of the element that has the `max-width`, not of the text inside it. If the body text is set slightly larger than the container's font, each line holds a few characters fewer than the token suggests. Measure a real paragraph once to confirm you land in the 65 to 75 range.

Generous space between the reading column and the sidebars matters as much as the column width. Use the spacing scale for the grid gap and step it up at larger breakpoints, so navigation never crowds the text on a wide screen.

## A naming trap: tokens that collide with utilities

Tailwind derives utility names from token names, and some namespaces generate more utilities than you might expect. A `--spacing-*` token creates `h-*`, `w-*`, `p-*` and `m-*`, but also the logical-size utilities `inline-*` and `block-*`.

This site once had a token called `--spacing-grid` for the size of a background grid. Tailwind dutifully generated `.inline-grid { inline-size: var(--spacing-grid) }`, which overrode the `display: inline-grid` utility, the class used by every round avatar and icon button. Every one of them stretched to 48 pixels wide.

<Callout type="warning">
  Never name a token after a Tailwind keyword: `grid`, `flex`, `block`, `table`, `hidden`, `contents`, `full`, `screen`. Prefer two-word names such as `band-cell`.
</Callout>

## Using the tokens in components

With the theme in place, components contain nothing but class names:

```tsx
export function TagLabel({children}: {children: ReactNode}) {
  return (
    <span className="inline-flex items-center rounded-full bg-primary-muted px-2.5 py-0.5 text-xs font-medium text-primary">
      {children}
    </span>
  )
}
```

Recurring combinations get a tiny helper rather than a CSS class. Buttons, for example:

```ts
const variants: Record<ButtonVariant, string> = {
  primary:
    'border-primary-solid bg-primary-solid text-fg-on-emphasis hover:bg-primary-solid-hover',
  secondary:
    'border-border bg-surface text-fg-strong hover:bg-surface-muted',
  ghost: 'border-transparent text-fg-muted hover:bg-surface-muted',
}

export const buttonClass = (variant: ButtonVariant, size: ButtonSize) =>
  cn(base, variants[variant], sizes[size])
```

The Prettier Tailwind plugin sorts classes inside `cn()` calls too, so diffs stay readable.

## Rules that keep the system honest

Tokens only work if the escape hatches stay closed. These are the rules this site enforces through review and tooling:

1. **No raw hex colours in components.** If a colour is missing, add a token.
2. **No inline `style` attributes.** Everything is a class.
3. **No pixel widths or heights in components.** Icon sizes and control sizes on the spacing scale are the only exceptions.
4. **Light and dark values land in the same commit.** A token without a dark value is a bug waiting for a dark-mode visitor.
5. **Arbitrary values must reference tokens.** `grid-cols-[var(--container-sidebar)_1fr]` is fine; `grid-cols-[240px_1fr]` is not.

Most of these can be checked mechanically: a search for `#[0-9a-f]{6}`, `style=` and `-[` followed by a number in component files finds nearly every violation.

## Checking accessibility from the tokens

Because every colour pair is named, contrast can be checked once for the whole site instead of per component. Compute the WCAG ratio for each foreground and background pair you actually use, in both themes:

| Pair                            | Light   | Dark    |
| ------------------------------- | ------- | ------- |
| `fg` on `canvas`                | 12.14:1 | 7.60:1  |
| `fg-muted` on `canvas`          | 5.64:1  | 5.10:1  |
| `primary` on `surface`          | 6.47:1  | 5.51:1  |
| `fg-on-emphasis` on `primary-solid` | 11.40:1 | 10.40:1 |

These numbers come from the real tokens on this site. When a pair fails, you fix one value and every component improves.

## Does it cost performance?

Hardly. Tailwind still generates only the utilities your source actually uses, so clearing the defaults makes the stylesheet slightly smaller, not larger. CSS variables add one level of indirection when the browser resolves a value, which is negligible next to layout and paint. Switching themes changes one attribute and the browser recalculates styles once; nothing is re-downloaded and no JavaScript walks the DOM.

The one real cost is upfront: every value has to be named before it can be used. That friction is the point. It turns "just this once" values into a conversation about whether the system is missing something.

## Migrating an existing project

You do not have to do this in one go:

1. Add semantic tokens alongside the defaults.
2. Replace classes component by component (`text-gray-500` to `text-fg-muted`).
3. Clear one namespace and fix whatever stops compiling.
4. Repeat until every namespace is cleared.
5. Delete the `dark:` colour prefixes; the variable swap now does their job.

Search and replace handles most of step 2, because a given default colour usually maps to one semantic token.

## What you get

After the migration, the whole visual language of the site is one file of a few hundred lines. Designers can tune colours, shadows and widths without reading TypeScript. Developers cannot drift from the system, because the drift does not compile. Dark mode costs one block of overrides instead of thousands of prefixes.

The site you are reading is built exactly this way. Open `src/main.css` in the repository to see every token, and notice that the components contain nothing but their names.

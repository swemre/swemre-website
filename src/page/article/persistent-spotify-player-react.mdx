Dropping a Spotify `<iframe>` into a page works until the visitor clicks a link. The route changes, the component unmounts, the iframe is destroyed and the music stops. This article builds a player that survives navigation, plays any track from a list with one click, shows Spotify-style play and pause states in that list, and falls back gracefully when the Spotify script is blocked. Everything here runs on this site: press play on any song on the home page and then keep browsing.

## What we are building

The requirements, written down before any code:

- A track list that looks like Spotify's: track number, a play button on hover, animated equalizer bars while playing, artwork, title and artist.
- **One** player, docked bottom right, shared by the whole site.
- Playback continues while the visitor moves between pages.
- The player can collapse to a mini bar without stopping the music.
- Closing the player stops playback and removes the embed.
- If Spotify's script cannot load, the visitor can still listen.
- Nothing from Spotify's player loads until the visitor presses play.

That last requirement is about privacy and performance. Spotify's embed sets cookies and loads a fair amount of JavaScript; a visitor who never presses play should not pay for it.

## Why a plain iframe is not enough

Spotify offers two ways to embed a track:

| Approach              | Control from your page                  | Survives navigation |
| --------------------- | --------------------------------------- | ------------------- |
| Plain embed `iframe`  | None; the visitor clicks inside it      | Only if never unmounted |
| iFrame API controller | `play`, `pause`, `loadUri`, events      | Only if never unmounted |

The plain iframe cannot be told to play from outside, so a play button in your own list cannot start it. The iFrame API exposes a controller you can drive from JavaScript. Neither approach survives an unmount, though, so the architecture has to keep the iframe alive.

## Step 1: mount once, above the router outlet

React Router's layout routes render a shared shell around every page. Anything in the layout, outside the `<Outlet />`, stays mounted while the visitor navigates:

```tsx
export function SiteLayout() {
  return (
    <div className="flex min-h-dvh flex-col">
      <Navbar />
      <Outlet />
      <Footer />
      <Dock />
    </div>
  )
}
```

`<Dock />` holds the player panel (and, on this site, the chat widget). Pages come and go inside `<Outlet />`; the dock never unmounts, so neither does the iframe inside it.

The dock is a fixed column in the bottom-right corner. Its container uses `pointer-events-none` so the empty space between panels does not block clicks on the page, and each panel opts back in with `pointer-events-auto`.

## Step 2: load the iFrame API once, on demand

Spotify's iFrame API is a script that, when loaded, calls a global function named `onSpotifyIframeApiReady` with the API object. Callback-style globals are awkward in React, so wrap the whole thing in a cached promise:

```ts
const SCRIPT_SRC = 'https://open.spotify.com/embed/iframe-api/v1'

let pending: Promise<SpotifyIframeApi> | null = null

export function loadSpotifyIframeApi(): Promise<SpotifyIframeApi> {
  if (pending) return pending
  pending = new Promise((resolve, reject) => {
    const spotifyWindow: SpotifyWindow = window
    spotifyWindow.onSpotifyIframeApiReady = resolve
    const script = document.createElement('script')
    script.src = SCRIPT_SRC
    script.async = true
    script.onerror = () => {
      pending = null
      script.remove()
      reject(new Error('Spotify iFrame API failed to load'))
    }
    document.body.appendChild(script)
  })
  return pending
}
```

Three details matter:

1. **The promise is cached in a module variable**, so calling the loader from several places injects the script exactly once.
2. **On error, the cache is cleared** and the script tag removed. A visitor whose network hiccupped can press play again and get a fresh attempt.
3. **It is only called from the play handler**, never on page load. That is how "nothing loads until play" is enforced.

The `SpotifyWindow` type is a small interface that extends `Window` with the optional callback, so the assignment is type-safe without a cast.

## Step 3: a provider that owns playback

Playback state is global: the song list on the home page, the dock and the search dialog (which can play songs) all need it. A context provider owns it:

```ts
interface PlayerState {
  current: Song | null
  isPaused: boolean
  failed: boolean
  collapsed: boolean
}
```

The provider exposes that state plus a handful of actions: `toggle(song)`, `togglePlayback()`, `setCollapsed(value)`, `close()` and `attachHost(element)`.

### One controller, many tracks

The core of the provider is `toggle`. It handles three cases:

```ts
const toggle = (song: Song) => {
  const controller = controllerRef.current
  if (state.current?.id === song.id && controller) {
    controller.togglePlay()
    return
  }
  setState(s => ({...s, current: song, isPaused: true}))
  if (controller) {
    controller.loadUri(spotifyTrackUri(song.spotifyId))
    controller.play()
  } else if (!state.failed) {
    mount(song)
  }
}
```

- **Same song, controller exists**: pause or resume.
- **Different song, controller exists**: swap the track in the existing embed with `loadUri`. No new iframe, no reload.
- **No controller yet**: load the API and create one.

Reusing one controller is important. Creating an embed per song would stack iframes and leave old ones playing.

### Creating the controller

```ts
const mount = (song: Song) => {
  loadSpotifyIframeApi()
    .then(api => {
      const host = hostRef.current
      if (!host) return
      const target = document.createElement('div')
      host.replaceChildren(target)
      api.createController(
        target,
        {uri: spotifyTrackUri(song.spotifyId), width: '100%', height: 152},
        controller => {
          controllerRef.current = controller
          controller.addListener('ready', () => controller.play())
          controller.addListener('playback_update', event =>
            setState(s => ({...s, isPaused: event.data.isPaused})),
          )
        },
      )
    })
    .catch(() => setState(s => ({...s, failed: true})))
}
```

The API **replaces** the element you give it with an iframe. Handing it a fresh child of the host, rather than the host itself, keeps the host element (which React owns) intact.

The `playback_update` listener is what keeps the UI honest. The visitor can also press play and pause inside the Spotify embed itself; because state comes from the controller's events rather than from our own button clicks, every play button on the site stays in sync either way.

Height 152 is the compact embed size Spotify supports. On this site that number also exists as a design token, `--spacing-embed`, so the host element and the API agree.

## Step 4: keep refs out of context

The provider needs to know which DOM element hosts the embed, and that element lives in the dock component. The obvious approach is to put a ref object into context and attach it in the dock. With the React Compiler enabled, that backfires: once a ref is part of the context value, the compiler treats reads of the whole value as ref reads during render, and the lint rules start flagging ordinary code.

The fix is to keep the ref local to the component that owns the element, and register the element with a callback in an effect:

```tsx
export function SpotifyPanel({forceCollapsed}: {forceCollapsed: boolean}) {
  const player = usePlayer()
  const hostRef = useRef<HTMLDivElement>(null)
  const {attachHost} = player

  useEffect(() => {
    attachHost(hostRef.current)
    return () => attachHost(null)
  }, [attachHost])

  // …
}
```

Inside the provider, `attachHost` writes into a private ref. The context value contains only plain state and functions, and the compiler is happy.

## Step 5: a panel that is always mounted

The panel component is rendered even when nothing is playing; it is simply hidden with a `hidden` class. That keeps the host element in the DOM from the start, so the provider always has somewhere to create the embed.

The visible part is a compact header: artwork, "Now playing" or "Paused", title and artist, a round green play/pause button, a collapse chevron and a close button. Below it sits the embed host.

### Collapse without stopping the music

Collapsing must hide the embed but keep it playing. Unmounting would destroy it. `display: none` is risky too: some browsers throttle or unload hidden iframes. Zero height with hidden overflow keeps the frame rendered and audible:

```tsx
<div className={cn('px-2.5', collapsed ? 'h-0 overflow-hidden' : 'pb-2.5')}>
  <div ref={hostRef} className="h-embed overflow-hidden rounded-md" />
</div>
```

The chat widget uses the same mechanism. When the chat panel opens, the player is forced into its collapsed mini bar so the two do not fight for space, and the music carries on.

<Callout type="warning">
  Test collapse behaviour in every browser you support. The zero-height approach worked everywhere I tried, but iframe throttling policies change between releases.
</Callout>

### Closing

`close()` calls `controller.destroy()`, clears the controller ref, empties the host and resets `current`. The next play starts from scratch.

## Step 6: a Spotify-style track list

Each song row is a single `<button>` laid out as a four-column grid: index, artwork, title and artist, Spotify mark. The whole row is clickable, which makes it an easy target on touch screens.

The first column changes with state:

| State                     | First column shows                    |
| ------------------------- | ------------------------------------- |
| Idle                      | Track number                          |
| Idle, hovered             | Play icon                             |
| Current, playing          | Animated equalizer                    |
| Current, playing, hovered | Pause icon                            |
| Current, paused           | Green play icon, green title          |

The equalizer is three thin bars with one keyframe animation and staggered delays:

```tsx
const barDelays = ['', '[animation-delay:-300ms]', '[animation-delay:-600ms]']

function Equalizer() {
  return (
    <span aria-hidden="true" className="flex h-3.5 items-end gap-0.5">
      {barDelays.map(delay => (
        <span
          key={delay}
          className={cn(
            'h-full w-0.75 origin-bottom animate-eq rounded-xs bg-spotify',
            delay,
          )}
        />
      ))}
    </span>
  )
}
```

The keyframes scale each bar between 30 % and 100 % of its height from the bottom edge. Negative delays start the bars at different points of the cycle, which is what makes it look like music rather than a metronome.

The button's accessible name changes with state, for example "Pause Midnight City by M83", and the equalizer is hidden from assistive technology. Screen reader users hear what the button will do, not a description of moving bars.

## Step 7: the fallback

If the API script fails (ad blockers and strict privacy extensions block it fairly often), the provider sets `failed`. The panel then renders a plain embed iframe for the current song instead of the controlled one:

```tsx
{player.failed && song ? (
  <iframe
    title={`${song.title} on Spotify`}
    src={spotifyEmbedUrl(song.spotifyId)}
    allow="autoplay; clipboard-write; encrypted-media; fullscreen; picture-in-picture"
    loading="lazy"
    className="block h-embed w-full rounded-md border-0"
  />
) : (
  <div ref={hostRef} className="h-embed overflow-hidden rounded-md" />
)}
```

The visitor loses the custom play buttons in the list (the embed has to be started inside the iframe) but can still listen. Degrading to "works, slightly less nicely" beats an error message.

## Artwork without the player

The song list shows album art, which is a static image from Spotify's CDN. I looked up each track once with Spotify's public oEmbed endpoint, which returns the thumbnail URL for a track link, and stored the URL alongside the track id. The page loads plain images, with no API call and no Spotify script.

Those images still reach Spotify's servers, so the privacy policy says so explicitly, along with what happens once the visitor presses play.

## Things Spotify decides for you

Some behaviour is outside your control and worth stating near the player:

- **Visitors not logged in to Spotify hear a 30-second preview.** That is Spotify's rule for anonymous embeds.
- **Autoplay policies apply.** The first `play()` works because it follows a click; programmatic playback without a gesture may be blocked.
- **The embed has a fixed set of sizes.** Design around 152 pixels (compact) or 352 pixels (full).

## Testing the player

Real audio is hard to test automatically, so the tests focus on the parts you own:

- With a stubbed API on `window`, the first `toggle` injects the script exactly once and calls `createController` once.
- Toggling the same song calls `togglePlay`; a different song calls `loadUri` and `play`.
- `close` calls `destroy` and clears `current`.
- Firing the script's `onerror` sets `failed` and renders the fallback iframe.
- In an end-to-end test, navigating between pages keeps the same iframe element in the DOM.

Actual playback, logged in and logged out, remains a manual check before each release.

## Summary

A persistent player is mostly an architecture problem. Mount it in the layout, not the page. Load the third-party script once, on demand, behind a cached promise. Keep one controller and swap tracks with `loadUri`. Drive the UI from the controller's events. Hide with zero height instead of unmounting, keep refs local to their owners, and always have a fallback. Do that, and the music keeps playing no matter where the visitor goes.

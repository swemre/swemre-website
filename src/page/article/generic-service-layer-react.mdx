Most front ends start with a hard-coded array and end with `fetch` calls sprinkled across forty components. Somewhere in between, someone has to find every place that reads data and rewrite it. A thin, generic service layer avoids that moment: you start with the array, components ask a service for data, and the day an API exists you change the service, not the components. This article builds that layer in TypeScript and React, using the code that runs this site.

## The problem with importing data directly

The fastest way to show a list of articles is to import the array:

```tsx
import {articles} from '../data/articles'

export function ArticleList() {
  return articles.map(article => <ArticleRow key={article.id} {...article} />)
}
```

It works, and it is a trap. Every component that imports the array assumes three things that will stop being true:

1. **Data is synchronous.** A network call is not.
2. **Data is always there.** A network call can fail or be slow.
3. **There is one source.** Tests, previews and storybooks all want different data.

When those assumptions break, the fix touches every importer. The service layer moves the assumptions into one place.

## Designing the contract

Every entity in the system has an id. That is the only thing the generic layer needs to know:

```ts
interface Entity {
  id: string
}

type NewEntity<T extends Entity> = Omit<T, 'id'>
```

`NewEntity<T>` is the shape you pass when creating something: everything except the id, which the service assigns.

The service contract is five operations:

```ts
interface SwemreService<T extends Entity> {
  findAll(): Promise<T[]>
  findById(id: string): Promise<T | undefined>
  create(data: NewEntity<T>): Promise<T>
  update(id: string, patch: Partial<NewEntity<T>>): Promise<T | undefined>
  remove(id: string): Promise<boolean>
}
```

A few choices here are deliberate:

- **Everything returns a `Promise`**, even when the data is in memory. Callers are written for a network from day one, so switching to one is invisible.
- **Missing is `undefined`, not an exception.** A missing article is a normal outcome ("not found" page), not an error.
- **`update` takes a partial patch.** Callers send only what changed, which maps cleanly to `PATCH` later.
- **`remove` returns a boolean**, so callers can tell "deleted" from "was not there".

## The first implementation: an array

An abstract class implements the contract over an array. Concrete services only pass in their rows:

```ts
export abstract class ArrayService<T extends Entity>
  implements SwemreService<T>
{
  protected readonly rows: T[]

  protected constructor(rows: T[]) {
    this.rows = rows
  }

  findAll(): Promise<T[]> {
    return Promise.resolve([...this.rows])
  }

  findById(id: string): Promise<T | undefined> {
    return Promise.resolve(this.rows.find(row => row.id === id))
  }

  create(data: NewEntity<T>): Promise<T> {
    const row = {...data, id: crypto.randomUUID()} as T
    this.rows.push(row)
    return Promise.resolve(row)
  }

  update(id: string, patch: Partial<NewEntity<T>>): Promise<T | undefined> {
    const index = this.rows.findIndex(row => row.id === id)
    if (index < 0) return Promise.resolve(undefined)
    this.rows[index] = {...this.rows[index], ...patch}
    return Promise.resolve(this.rows[index])
  }

  remove(id: string): Promise<boolean> {
    const index = this.rows.findIndex(row => row.id === id)
    if (index < 0) return Promise.resolve(false)
    this.rows.splice(index, 1)
    return Promise.resolve(true)
  }
}
```

Note that `findAll` returns a **copy**. A caller that sorts the result in place must not reorder the service's own data. It is a one-character habit that prevents a whole class of "why did the list change order" bugs.

<Callout type="note">
  The constructor assigns `this.rows` explicitly instead of using a TypeScript parameter property. This project compiles with `erasableSyntaxOnly`, which forbids syntax that cannot simply be stripped, so Node can run the same files with type stripping.
</Callout>

## Concrete services

A concrete service is a few lines, plus the queries that make sense for its entity:

```ts
export class ArticleService extends ArrayService<Article> {
  constructor() {
    super(articleDatabase)
  }

  override async findAll(): Promise<Article[]> {
    const all = await super.findAll()
    return all.sort((a, b) => +new Date(b.createdAt) - +new Date(a.createdAt))
  }

  findBySlug(slug: string): Promise<Article | undefined> {
    return Promise.resolve(this.rows.find(row => row.slug === slug))
  }
}
```

Ordering is a service concern. Every page that lists articles gets them newest first without repeating the sort, and the day the API sorts on the server, the override simply goes away.

Some services add operations that are not CRUD at all. The contact form service has `submitResumeRequest(input)`, which stamps the record with a kind and a timestamp before storing it. Domain operations belong on the service, named after what they do.

## The second implementation: localStorage

Some data should survive a reload but has no server yet. A subclass persists after every write:

```ts
export abstract class LocalStorageService<T extends Entity>
  extends ArrayService<T>
{
  private readonly key: string

  protected constructor(key: string) {
    super(readRows<T>(key))
    this.key = key
  }

  override async create(data: NewEntity<T>): Promise<T> {
    const row = await super.create(data)
    this.persist()
    return row
  }

  private persist() {
    try {
      localStorage.setItem(this.key, JSON.stringify(this.rows))
    } catch {
      // Storage full or blocked: keep the in-memory copy.
    }
  }
}
```

`update` and `remove` are overridden the same way. Reading tolerates junk:

```ts
function readRows<T>(key: string): T[] {
  try {
    const value: unknown = JSON.parse(localStorage.getItem(key) ?? '[]')
    return Array.isArray(value) ? (value as T[]) : []
  } catch {
    return []
  }
}
```

The chat widget on this site is a `LocalStorageService<Conversation>`. Conversations survive reloads, and when a backend exists, `ChatService` changes its parent class. Its methods (`start`, `send`, `presence`) stay the same.

## A typed registry

Components should not construct services. If they did, each component would hold its own copy of the data, and tests could not swap anything out. One registry creates every service once:

```ts
const entityServices = {
  article: new ArticleService(),
  chat: new ChatService(),
  contactForm: new ContactFormService(),
  project: new ProjectService(),
  song: new SongService(),
  specialPage: new SpecialPageService(),
}

export const serviceRegistry: ServiceMap = {
  ...entityServices,
  search: createSearchService(entityServices),
}
```

`ServiceMap` maps each name to its concrete class, not to the generic interface:

```ts
interface ServiceMap {
  article: ArticleService
  chat: ChatService
  contactForm: ContactFormService
  project: ProjectService
  search: SearchService
  song: SongService
  specialPage: SpecialPageService
}
```

That detail is what makes entity-specific methods available without casts.

## Reaching services from React

The registry goes into a context, and a one-line hook reads it:

```ts
export function useService<K extends keyof ServiceMap>(
  name: K,
): ServiceMap[K] {
  return useContext(ServiceContext)[name]
}
```

The generic `K` does the heavy lifting. `useService('article')` returns `ArticleService`, so `findBySlug` autocompletes. A misspelled name is a compile error. Nobody has to remember which file a service lives in.

The context's default value is the registry itself, so the app works without a provider. A `ServiceProvider` exists for the one place that needs to replace it: tests.

## Loading data in components

Promises need loading state. A small hook turns any loader into `{data, loading}`:

```ts
export function useAsyncData<T>(loader: () => Promise<T>): AsyncResult<T> {
  const [settled, setSettled] = useState<AsyncSettled<T> | null>(null)

  useEffect(() => {
    let live = true
    void loader().then(data => {
      if (live) setSettled({loader, data})
    })
    return () => {
      live = false
    }
  }, [loader])

  const ready = settled !== null && settled.loader === loader
  return {data: ready ? settled.data : undefined, loading: !ready}
}
```

Two techniques make it correct:

- **The `live` flag** ignores results that arrive after the component unmounted or the loader changed, avoiding stale updates.
- **Storing the loader with its result** means `loading` is derived, not set. When the loader changes (a new slug), the old data is immediately treated as stale, without an extra state update inside the effect.

<Callout type="warning">
  The loader must be referentially stable. Wrap it in `useCallback` with its real dependencies, otherwise every render creates a new loader and starts a new load.
</Callout>

A convenience hook covers the most common case:

```ts
export function useFindAll<T extends Entity>(service: SwemreService<T>) {
  const loader = useCallback(() => service.findAll(), [service])
  return useAsyncData(loader)
}
```

And a page reads naturally:

```tsx
export default function ProjectsPage() {
  const projects = useFindAll(useService('project'))

  if (projects.loading) return <p>Loading…</p>
  return <ProjectGrid items={projects.data ?? []} />
}
```

For a lookup with a parameter, build the loader with `useCallback`:

```tsx
const service = useService('article')
const loader = useCallback(() => service.findBySlug(slug), [service, slug])
const {data: article, loading} = useAsyncData(loader)
```

### A known gap: errors

The hook above has no error state. If a loader rejects, the page stays on "Loading…" forever. With in-memory services that cannot happen, which is why it was acceptable to start with. Before the first HTTP service lands, `AsyncResult` gains an `error` field and pages render a retry message. Writing the gap down in the project's risk register keeps it from being forgotten.

## Search as a consumer of services

Services also make cross-cutting features simple. The site-wide search dialog does not know about articles or projects. It knows about a `Searchable` shape (an id, a title, an optional summary and tags) and accepts sources:

```ts
new SearchService()
  .register({
    category: 'Articles',
    icon: 'file',
    load: () => services.article.findAll(),
    action: article => ({kind: 'navigate', to: `/articles/${article.slug}`}),
  })
  .register({
    category: 'Songs I liked',
    icon: 'spotify',
    load: () => services.song.findAll(),
    action: song => ({kind: 'play-song', song}),
  })
```

Adding a new searchable entity is one `register` call. Because each source loads through its service, search automatically reads from the API once the services do.

## Testing becomes trivial

Because pages only ever call `useService`, a test can supply a different registry:

```tsx
class FakeArticles extends ArrayService<Article> {
  constructor() {
    super([testArticle])
  }
}

render(
  <ServiceProvider services={{...serviceRegistry, article: new FakeArticles()}}>
    <MemoryRouter initialEntries={['/articles']}>
      <ArticlesPage />
    </MemoryRouter>
  </ServiceProvider>,
)
```

No network mocking, no module patching and no global setup. The same trick powers previews: render a page with a registry full of edge cases (very long titles, empty lists, unusual characters) and look at it.

Services themselves are plain classes, so unit tests need no React at all: create, update, remove and check the results.

## When to graduate to HTTP

Stay with arrays while the data is authored by you and changes only on deploy. Move to HTTP when data must be shared between users or devices, or written by someone other than the developer.

The move looks like this:

1. Write `HttpService<T>` implementing `SwemreService<T>` with `fetch`, mapping `404` to `undefined` and `false`.
2. Change the parent class of each service that should go remote.
3. Add error handling to `useAsyncData`.
4. Keep `ArrayService` for tests and for data that stays static.

```ts
export abstract class HttpService<T extends Entity>
  implements SwemreService<T>
{
  private readonly baseUrl: string

  protected constructor(baseUrl: string) {
    this.baseUrl = baseUrl
  }

  async findById(id: string): Promise<T | undefined> {
    const response = await fetch(`${this.baseUrl}/${id}`)
    if (response.status === 404) return undefined
    if (!response.ok) throw new Error(`HTTP ${response.status}`)
    return (await response.json()) as T
  }
}
```

## Where things live

A service layer only stays useful if its boundaries stay clear. A few placement rules keep it that way:

- **Services know nothing about React.** No hooks, no JSX, no context inside `services/`. That keeps them testable in plain Node and reusable from scripts.
- **Hooks know nothing about storage.** `useAsyncData` does not care whether a promise came from an array or from `fetch`.
- **Pages never import `database/`.** The arrays are the services' private implementation detail, even though they are just exported constants.
- **Domain operations get domain names.** `submitResumeRequest` and `send` say what happens; a generic `create` with a magic flag would not.

When a rule has to be broken (this site has one page that writes to the interaction store directly), write the exception down so it can be cleaned up later rather than copied.

## Trade-offs

A service layer is not free:

- **Ceremony for static data.** Wrapping a constant array in a class and a promise feels heavy for a list of five songs.
- **One more indirection** when reading code: from the page to the hook to the registry to the service.
- **Async everywhere**, which means loading states even for data that is technically instant.

For a project that expects to grow a backend, those costs buy a lot: every data access is in one folder, every component is testable with fakes, and the migration to a real API is a change in the services rather than a rewrite of the UI.

## Summary

Start with one interface and five methods. Make everything asynchronous. Implement it over an array, add a persisting subclass when you need one, register instances once, and reach them through a typed hook. Components stay ignorant of where data comes from, and that ignorance is exactly what lets you change the answer later.

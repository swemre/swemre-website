MDX lets you write prose in Markdown and drop React components right into it. For a portfolio or a technical blog that is close to ideal: articles stay pleasant to write, but they are also real modules in your build, so they are typed, bundled, code-split and checked by the same tools as the rest of your application. This article walks through a complete setup in a Vite and React project, from the first install to lazy loading, custom components, a table of contents and the small gotchas that cost me an afternoon each.

## Why MDX instead of plain Markdown?

Plain Markdown is wonderful until you need something it cannot express. A warning box, a tabbed code sample, a small interactive demo or a chart all end up as raw HTML pasted into the file, or as a custom syntax that a parser has to understand at runtime. MDX solves this by treating a Markdown file as a JSX module:

- **Markdown ergonomics** for the 95 % of the text that is headings, paragraphs, lists, links and code.
- **JSX where it matters**: callouts, diagrams, live examples, anything you can render in React.
- **Build-time compilation**: the MDX compiler turns each file into a React component during the build, so no Markdown parser ships to the browser.
- **Imports and exports**: an article can import a component or a data file and export values, just like a `.tsx` file.

> Content becomes just another module in your dependency graph.

That last point is the important one. Because an article is a module, the bundler can split it into its own chunk, tree-shake what it does not use and fail the build when it imports something that does not exist.

### What MDX is not

MDX is not a CMS. There is no editor UI, no drafts workflow and no preview server beyond your normal dev server. If non-developers need to write content, pair MDX with a Git-based CMS or pick a headless CMS instead. For a personal site written by one developer, the repository is the CMS, and that is a feature: every change is reviewed, versioned and deployed like code.

## Installing the pieces

A Vite and React project needs three packages for the basics, plus optional plugins for tables and syntax highlighting:

```bash
npm install @mdx-js/rollup @mdx-js/react
npm install -D @types/mdx remark-gfm @shikijs/rehype
```

| Package            | Role                                                              |
| ------------------ | ----------------------------------------------------------------- |
| `@mdx-js/rollup`   | Compiles `.mdx` files during the build (Vite uses Rollup plugins) |
| `@mdx-js/react`    | Provides `MDXProvider` so components can be injected everywhere   |
| `@types/mdx`       | Types for `import Post from './post.mdx'`                         |
| `remark-gfm`       | GitHub-flavoured Markdown: tables, task lists, strikethrough      |
| `@shikijs/rehype`  | Syntax highlighting at build time with VS Code themes             |

## Configuring Vite

The MDX plugin must run **before** the React plugin. MDX outputs JSX, and the React plugin is what transforms JSX (and, in this project, runs the React Compiler). If the order is wrong, Vite tries to parse JSX that nothing has transformed and the build fails with a confusing syntax error.

```ts
import mdx from '@mdx-js/rollup'
import rehypeShiki from '@shikijs/rehype'
import react from '@vitejs/plugin-react'
import remarkGfm from 'remark-gfm'
import {defineConfig} from 'vite'

export default defineConfig({
  plugins: [
    {
      enforce: 'pre',
      ...mdx({
        providerImportSource: '@mdx-js/react',
        remarkPlugins: [remarkGfm],
        rehypePlugins: [
          [
            rehypeShiki,
            {
              themes: {light: 'github-light', dark: 'github-dark-dimmed'},
              defaultColor: false,
            },
          ],
        ],
      }),
    },
    react({include: /\.(mdx|js|jsx|ts|tsx)$/}),
  ],
})
```

Three details deserve a closer look:

1. `enforce: 'pre'` moves the MDX plugin ahead of everything else.
2. `providerImportSource` tells the compiler to read components from the nearest `MDXProvider`. Without it, components have to be passed as props to every article.
3. `react({include: ...})` adds `.mdx` to the files the React plugin handles, so Fast Refresh works while you write.

### TypeScript

Add the MDX types to the app's `tsconfig`:

```json
{
  "compilerOptions": {
    "types": ["vite/client", "mdx"]
  }
}
```

Now `import Post from './post.mdx'` is typed as a component that accepts an optional `components` prop.

## Your first article

Create `post.mdx`:

```text
## Hello

This is **Markdown** with a <Callout type="tip">component</Callout> inside.
```

Then import and render it like any other component:

```tsx
import Post from './post.mdx'

export const Page = () => <Post />
```

That is a working setup. Everything after this point is about making it scale beyond three articles.

## Separating metadata from bodies

Most MDX setups put metadata in front matter at the top of the file. That works, but it has costs: front matter needs another plugin, it is untyped YAML, and a listing page has to import every article body just to read the titles.

This site takes a different approach. Metadata lives in a typed array, and bodies live in `.mdx` files named after the slug:

```ts
export const articleDatabase: Article[] = [
  {
    id: 'a1f3c9d2',
    slug: 'getting-started-with-mdx',
    title: 'Getting Started with MDX in a Vite + React App',
    summary: 'Write long-form content in Markdown and ship it in your bundle.',
    author: 'swemre',
    createdAt: '2026-09-02T09:00:00Z',
    readingTime: 10,
    tags: ['mdx', 'react', 'vite'],
  },
]
```

The benefits are immediate:

- The compiler checks every field. A missing `summary` or a misspelled tag key fails the build.
- The articles index, the RSS feed and the search dialog read titles without loading any body.
- The slug is the single link between the two halves, which is easy to test.

## Lazy loading every body

Importing every article statically would put all of them in the main bundle. Vite's `import.meta.glob` solves that. With the default (lazy) mode it returns a map of file paths to import functions, and each function becomes its own chunk:

```ts
const modules = import.meta.glob<{default: ComponentType}>(
  '../page/article/*.mdx',
)
```

Combine it with `React.lazy` to get a component per slug:

```ts
import {lazy, type ComponentType} from 'react'

type MdxModules = Record<string, () => Promise<{default: ComponentType}>>

export const lazyBodies = (
  modules: MdxModules,
): Record<string, ComponentType> =>
  Object.fromEntries(
    Object.entries(modules).map(([path, loader]) => [
      path.replace(/^.*\/|\.mdx$/g, ''),
      lazy(loader),
    ]),
  )

const bodies = lazyBodies(modules)
```

<Callout type="warning">
  Build this map once, at module load. Calling `lazy()` during render creates a new component on every render, which remounts the article and loses its state. The React Compiler's `static-components` rule flags exactly this mistake.
</Callout>

Render the lazy component inside `Suspense`, and you have per-article code splitting:

```tsx
export function MdxBody({
  body: Body,
  components,
}: {
  body: ComponentType
  components: MDXComponents
}) {
  return (
    <MDXProvider components={components}>
      <Suspense fallback={<p>Loading…</p>}>
        <Body />
      </Suspense>
    </MDXProvider>
  )
}
```

After a production build you can see the result in the output: one small chunk per article, downloaded only when someone opens it.

## Styling Markdown with a component map

MDX renders Markdown as ordinary HTML elements (`h2`, `p`, `ul`, `table`, `code`). `MDXProvider` lets you replace each one with a component, which is the cleanest way to style content without a global stylesheet:

```tsx
export const docsMdxComponents: MDXComponents = {
  p: props => <p className="my-4" {...props} />,
  a: props => (
    <a className="font-medium text-primary hover:underline" {...props} />
  ),
  table: props => (
    <div className="my-5 overflow-x-auto">
      <table className="w-full border-collapse text-sm" {...props} />
    </div>
  ),
  Callout,
}
```

The last entry, `Callout`, is not an HTML element at all. Anything you put in the map becomes available in every MDX file **without an import**, which keeps articles short and makes it easy to replace a component site-wide later.

Different page types can use different maps. This site uses one map for articles and projects and another for legal pages, where `h2` headings are numbered automatically with a CSS counter.

## Headings, anchors and a table of contents

Documentation-style pages need linkable headings and an "On this page" list. Both come from the component map.

The `h2` and `h3` entries render an `AnchorHeading` that gives each heading an id derived from its text, plus a small `#` link that appears on hover:

```tsx
h2: props => <AnchorHeading as="h2" {...props} />
```

A hook then scans the rendered body for headings and builds the table of contents. Because the body is lazy, the headings do not exist on the first render, so the hook watches the container with a `MutationObserver` and rescans when the content arrives:

```ts
const observer = new MutationObserver(scan)
observer.observe(root, {childList: true, subtree: true})
```

A second hook uses `IntersectionObserver` to highlight the heading currently in view. Together they give you the scroll-spy behaviour readers expect from docs sites, with no plugin and no build step.

## Syntax highlighting at build time

Client-side highlighters are heavy: a grammar for every language and a theme engine, all shipped to every reader. Shiki runs in the build instead and outputs plain HTML with colours already applied.

With `defaultColor: false`, Shiki emits both themes as CSS variables on every token:

```html
<span style="--shiki-light:#D73A49;--shiki-dark:#F47067">const</span>
```

Two small CSS rules pick the right variable based on the active theme:

```css
.shiki,
.shiki span {
  color: var(--shiki-light);
}

[data-theme='dark'] .shiki,
[data-theme='dark'] .shiki span {
  color: var(--shiki-dark);
}
```

Theme switching is instant, and the browser never downloads a highlighter. Remember to give every code fence a language; a fence without one is rendered as plain text.

## Writing rules that keep MDX happy

MDX is stricter than Markdown because it is also JSX. These are the rules I keep relearning:

1. **Curly braces are expressions.** Writing `{name}` in prose evaluates `name`. Put literal braces inside backticks or escape them.
2. **A bare less-than sign starts a tag.** `a < b` in prose can break the parser. Use inline code for comparisons.
3. **Blank lines around block components.** Markdown inside a component is only parsed as Markdown when it is separated by blank lines.
4. **Comments use JSX syntax.** HTML comments do not work; write them as JSX comments with braces.
5. **No `h1` in the body.** The page template renders the title. Starting the body at `##` keeps the heading hierarchy correct for screen readers and for the table of contents.

<Callout type="note">
  Prettier formats MDX, but it can mangle JSX comments at the top of a file. This project excludes `.mdx` from Prettier and keeps the license header as a JSX comment.
</Callout>

## Feeding RSS and search from the same data

Because metadata is a plain typed array, other consumers can use it without touching MDX at all.

The RSS feed is generated by a small Node script that imports the same database file. Node 22 can strip TypeScript types at load time, so the script reads `articleDatabase.ts` directly:

```bash
node --experimental-strip-types scripts/generate-rss.mjs
```

The script runs automatically before `dev` and `build`, so the feed can never fall out of date. The only constraint is that the database file must use type syntax Node can erase: no enums, no parameter properties, and `import type` for type-only imports.

Search works the same way. The search service registers a source that loads article metadata and maps it to search documents. Titles, summaries and tags are searchable without downloading a single article body.

## Testing the setup

A few cheap tests catch most content mistakes:

- **Every metadata entry has a body**, and every `.mdx` file has an entry. A mismatch means a listed article that 404s, or an orphaned file.
- **Slugs and ids are unique** and well formed.
- **Dates parse** and are in UTC.
- **The build output contains one chunk per article**, proving that lazy loading still works after a refactor.

The first check is a few lines once `getBody(slug)` exists:

```ts
for (const article of articleDatabase) {
  expect(service.getBody(article.slug)).toBeDefined()
}
```

## Performance notes

On this site the home page loads no article code at all. An article page loads its own chunk (usually a few kilobytes of compiled JSX) plus the shared MDX runtime, which is small. Code is already highlighted, images can be lazy, and the table of contents is computed from the DOM rather than shipped as data.

If you have hundreds of articles, the metadata array itself becomes the largest piece. At that point, split it per year or move it to a JSON file loaded on the index page only.

## Common errors and fixes

| Symptom                                           | Likely cause                                         |
| ------------------------------------------------- | ---------------------------------------------------- |
| `Unexpected token` in an `.mdx` file during build | MDX plugin runs after the React plugin               |
| Component is undefined inside an article          | Missing from the `MDXProvider` map, or no `providerImportSource` |
| Article remounts and loses state                  | `lazy()` called during render                        |
| Table renders as text                             | `remark-gfm` not installed or not configured         |
| Code is not coloured                              | Fence has no language, or the Shiki CSS rules are missing |
| Parse error on a sentence with a brace            | Literal `{` in prose; wrap it in backticks           |

## Wrapping up

The setup in this article is small: one Vite plugin, one provider, a glob and a typed array. In return you get articles that are modules, code-split per page, highlighted at build time, styled through a single component map and fully typed from metadata to rendering.

Start simple, with a static import and one article. Add the glob when you have three. Add the component map when you write your first callout. Each step is independent, and each one makes the next article a little cheaper to write.
